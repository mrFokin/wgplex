# wgplex

Несколько WireGuard-туннелей одновременно на macOS с маршрутизацией по правилам.
Движок: демон и CLI в одном бинарнике, установка через Homebrew. Приложение — отдельный репозиторий `wgplex-app`, клиент публичного API.

## Источник истины

- `docs/design.md` — согласованный дизайн и план этапов (раздел 21). Код ему следует.
- `docs/api.md` — публичный контракт API (на английском). Меняется только в этом репозитории.
- Отклонение от дизайна — только после согласования с пользователем; правка `design.md` и `api.md` идёт в той же ветке, что и код.
- План этапа — `docs/plans/m<N>-<slug>.md` в ветке этапа: сигнатуры, файлы, задачи, «Факты spike», «Ход работы». Оркестратор отмечает в нём пройденные шаги.

## Принципы

- KISS: никаких абстракций (интерфейсов, реестров, обёрток) на будущее — только то, что нужно в текущей задаче.
- JSON-RPC — `github.com/mrFokin/jrpc/v2` без собственных обёрток. API: `go doc github.com/mrFokin/jrpc/v2`.
- Чистая логика отделена от системных вызовов и покрыта unit-тестами без root. Обращения к utun, `PF_ROUTE`, SCDynamicStore, Directory Services — тонкий слой поверх неё.
- Приватные ключи не попадают в логи, ответы API и тестовые фикстуры (в фикстурах — только сгенерированные ключи).
- Свои метки: маршруты — `RTF_PROTO2`, синтетический DNS-сервис — собственный UUID (design 4.1). Не путать с Wirefork, из которого скопирован код.

## Структура

```
cmd/wgplex/        бинарник: daemon и команды CLI
internal/config/   разбор и валидация wgplex.yaml и .conf, права файлов, сопоставление доменов
internal/router/   расчёт таблицы маршрутов и синхронизация с ядром
internal/dns/      резолвер, точечный захват системного DNS
internal/tunnel/   wireguard-go, utun
internal/health/   handshake, ping, HTTP, failover
internal/netwatch/ смена сети, сон
internal/rpc/      методы JSON-RPC, права по методам, урезание ответов
internal/state/    state.json: переключатели, пауза, снимок блокировки
scripts/           vm.sh и скрипты проверок
docs/              документация (на русском; api.md — на английском)
```

Пакеты создаются тогда, когда в них появляется код.

## Проверки

- `make check` — `gofmt -l` (пусто), `go vet ./...`, `go test ./...`. Должен быть зелёным перед каждым коммитом.
- `make build` — universal `build/wgplex`; `make release` — архив для формулы.

## Root и система

- На хосте агенты не запускают `sudo` и не меняют сетевые настройки (маршруты, DNS, интерфейсы), launchd и объекты входа.
- Внутри одноразовой VM tart (клоны `wgp-check-*` образа `wgp-base`) — можно, только через `scripts/vm.sh`: он работает только с такими клонами.
- VM — в bridged-сети (`--net-bridged`), чтобы туннели и DNS Wirefork на хосте не влияли на проверки; NAT — только при выключенных туннелях хоста (трафик VM идёт по маршрутам хоста, M0 B3), тестовые адреса и домены вне правил хоста.
- Конфиги туннелей хоста в VM не используются (один ключ у двух клиентов ломает туннель хоста). Тестовые туннели — отдельные пиры или WireGuard-сервер во второй VM.
- За пользователем, по шагам из плана этапа: шаги с GUI-диалогами в VM, действия на хосте, финальная проверка на хосте (сон, смена сети, реальные сети).

## Git

- Работа в ветках этапов `m<N>-<slug>`. В них можно коммитить без подтверждения после зелёного `make check`.
- Слияние в `master` — автоматически, если: `make check` зелёный на результате слияния; у `reviewer` нет блокеров, замечания исправлены или записаны в «Ход работы» как принятые; ручная проверка из плана пройдена (пользователь подтвердил); в ветке нет несогласованных правок `design.md` и `api.md`; слияние без конфликтов. Иначе — остановиться и спросить.
- Push и релизы (тег, `gh release`, обновление формулы в tap) — только после одобрения пользователя.
- Сообщения коммитов — conventional commits: префикс на английском, описание и тело на русском (`feat(config): права файлов конфига`), с завершающей строкой `Co-Authored-By`.
- Комментарии в коде, тексты CLI и демона, README, `api.md` — на английском; `design.md`, планы и коммиты — на русском.

## Сессии

| Сессия | Что делает |
|---|---|
| Дизайн | обсуждение продукта, правки `design.md` и `api.md` вне этапов. Код не пишет |
| Оркестратор этапа | одна сессия на этап: план этапа, агенты, сведение, «Ход работы», слияние |

Сессии и репозитории (`wgplex`, `wgplex-app`) связаны через документы и пользователя, без прямых сообщений. Вопрос дизайна во время этапа — пользователю; крупный — в сессию дизайна.

## Мультиагентный процесс

Оркестратор делит этап на задачи, составляет план этапа (сигнатуры пакетов, файлы, задачи) и согласует его с пользователем, запускает агентов, сводит результат.

| Агент | Роль |
|---|---|
| `go-dev` | реализация Go-кода |
| `test-dev` | тесты чистой логики по `design.md`, не глядя в реализацию |
| `reviewer` | ревью диффа: соответствие дизайну и правилам, ошибки, тесты |
| `Explore` / `Plan` (встроенные) | spike перед рискованным этапом: исследование и скрипт проверки |
| `general-purpose` (встроенный) | spike, которому нужно собирать помощников (бинарники, приложения, скрипты) |

Цикл задачи:

1. Оркестратор фиксирует план этапа; `go-dev` вводит сигнатуры (типы и функции без логики).
2. `go-dev` пишет реализацию, `test-dev` параллельно пишет `*_test.go` по дизайну. Файлы не пересекаются.
3. `reviewer` проверяет дифф. Если тест и код расходятся — решает, кто неправ; неясность в дизайне уходит пользователю.
4. Ветка сливается в `master` по условиям из раздела «Git».

Агенты, пишущие код, работают в отдельных worktree. Два пишущих агента не трогают одни и те же файлы.
Spike перед рискованным этапом — встроенным агентом `Explore`/`Plan`, если нужно собирать помощников — `general-purpose`; проверки, которым нужен root, — в VM через `scripts/vm.sh`, результат — в «Факты spike» плана этапа.

## Ответ оркестратора

Каждый ответ оркестратора пользователю заканчивается блоком:

```
Дальше:
- от вас: <решение | ручной шаг (что и где запускать) | ничего>
- в другую сессию: <готовый текст для вставки | —>
- следующий шаг: <что оркестратор сделает после ответа>
```

Этап, меняющий `api.md`, заканчивается текстом для сессии `wgplex-app`: версия движка, `api_version`, что добавлено. Тот же текст записывается в «Ход работы».
