# M5 — возврат на приоритетный туннель

Статус: план на согласовании (2026-11-05). Ветка `m5-failover` от `master` (802c578).

**Цель:** правило, ушедшее на резерв, возвращается на более приоритетный туннель из `via` (design 9.2): только туннель с `check`, после 5 минут подряд «жив» по проверке; смена сети и пробуждение обнуляют отсчёт; `config.reload` и явный `tunnel.enable` выбирают заново.

Правила — design 7.3, 9, 9.2, 21.1 (M5); CLAUDE.md.

## Контекст: состояние после M4

- `router.SelectRules(cfg, tunnels, prev)` оставляет правилу прежний туннель, пока он годен (`Up && Alive`), — «не возвращаться». Возврата нет вообще.
- `health.Health` хранит `State`, `Fails`, `LastOK`; времени перехода в `Alive` нет. `Reset(at)` (смена сети, сон) вердикты не трогает.
- `healthTick.observe` зовёт `reselect(d.rules)` только при смене `Alive()`; по времени ничего не срабатывает.
- `config.reload` и старт зовут `reselect(nil)` (выбор с нуля — это уже «сразу»). `tunnel.enable` зовёт `reselect(d.rules)`, а туннель при включении ещё `starting` (`tun == nil`), так что «сразу» для него не выполняется.

## Решения

1. **`Health.AliveSince time.Time`** — момент перехода активной проверки в `Alive` (первый успех после `Dead` или после `New`/`Reset`); нулевой, если `active != Alive` или `check` не задан. Сбрасывается в ноль при неудаче проверки (`Fails > 0`) и вердикте `Dead`.
2. **`Reset(at)`** ставит `AliveSince = at`, если активный вердикт `Alive` (отсчёт идёт заново от сброса, вердикт остаётся), иначе ноль. «Неизвестно» отсчёта не даёт.
3. **`Health.Returnable(now) bool`** (чистая): `active == Alive && !AliveSince.IsZero() && now − AliveSince ≥ ReturnAfter`, `ReturnAfter = 5 * time.Minute`. Пассивный «жив» (handshake, rx) возврата не даёт.
4. **`router.TunnelState.Return bool`** — туннель вправе принять правило обратно. `SelectRules`: правило с `prev[i].Tunnel` на позиции `k` в `via` переходит на первый `v` из `via[:k]` с `usable(v) && Return`. Прочее — как есть.
5. **Срабатывание по времени.** `observe` зовёт `reselect(d.rules)` и когда какой-то туннель впервые стал `Returnable` (флаг в `runTunnel`, чтобы не дёргать каждый тик) — не только при смене `Alive`. Возврат рвёт соединения правила один раз (это следствие смены маршрутов; отдельного кода нет).
6. **`tunnel.enable`.** Правило возвращается на включённый приоритетный туннель сразу, как тот поднялся (design 9.2), даже без 5 минут: при `starting → up` в `daemon` зовётся `reselect(nil)` вместо `reselect(d.rules)`, если туннель стоит в `via` выше текущего у какого-то правила. **Вопрос 1.**
7. **Лог и статус.** Строка `rule returned` в логе (правило, с какого на какой). В `status.get`/`api.md` изменений нет: правило, вернувшееся на цель, просто перестаёт быть «на резерве». `api_version` не меняется.
8. **`check` без `ReturnAfter`-флага в конфиге:** константы, в конфиг не выносятся (design 9).

## Не в M5

Формула и поставка (M6); приложение. Изменений `api.md` нет.

## Задачи и порядок

1. **Сигнатуры** (`go-dev`): поле/константа/метод без логики.
2. **Параллельно** (файлы не пересекаются):
   - A (`go-dev`, worktree): `internal/health` — `AliveSince`, `Reset`, `Returnable`.
   - B (`go-dev`, worktree): `internal/router/rules.go` — возврат в `SelectRules`.
   - T (`test-dev`): `Returnable` и сброс (фейковые часы: 4 мин 59 с — нет, 5 мин — да; без `check` — нет; неудача посреди отсчёта обнуляет; `Reset` обнуляет; только пассивный «жив» — нет); `SelectRules` (возврат на `Return`, не на `Alive` без `Return`; первый из нескольких приоритетных; правило в fallback берёт любой годный; `prev == nil` — выбор с нуля) — по design, не глядя в реализацию.
3. **Демон** (`go-dev`, после 2): `cmd/wgplex/health.go` и `daemon.go` — `Return` в `states()`, срабатывание по времени, `tunnel.enable`, лог.
4. **Ревью** (`reviewer`), исправления.
5. **Проверка в VM** (`general-purpose`, sonnet): стенд M2 — WireGuard-сервер во второй VM (два сервера: приоритетный `t1`, резервный `t2`), клиент с правилом `via: [t1, t2]`, у обоих `check`; bridged, `scripts/vm.sh`:
   1. остановить сервер `t1` → за ≤ 40 с правило на `t2`;
   2. вернуть сервер → правило остаётся на `t2` до 5 минут, затем (≤ 5 мин 10 с) возвращается на `t1`, лог `rule returned`;
   3. то же без `check` у `t1` → правило на `t2` остаётся сколько угодно (≥ 8 минут);
   4. смена сети (`networksetup`-переключение/смена шлюза в VM) на 4-й минуте отсчёта → возврат не раньше, чем через 5 минут после смены;
   5. `config.reload` на резерве при живом `t1` → правило сразу на `t1`; `tunnel.disable t1` + `enable` → сразу после подъёма.
6. **Документы:** «Ход работы»; правки design 9.2 по фактам; слияние по CLAUDE.md.

## Вопросы к пользователю

1. `tunnel.enable` приоритетного туннеля: возвращать правило сразу после подъёма (`reselect(nil)`, как `reload`), без ожидания 5 минут? (Рекомендация: да, как в design 9.2.)
2. Отсчёт после смены сети/сна идёт заново от сброса (туннель остаётся «живым», но 5 минут считаются с момента сброса), а не «пока не подтвердится первой проверкой»? (Рекомендация: заново от сброса.)
3. Прогон VM — те же ограничения, что в M4 (bridged, `wgp-check-m5-*`, клоны сносятся)? (Рекомендация: да.)
