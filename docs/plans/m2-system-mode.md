# M2 — системный режим

> Статус: done
> Владелец: оркестратор · Проверено: «да» пользователя: 2026-10-21

**Цель:** демон работает как системная служба по design 4.1: сам читает каталог конфига, состояние переключателей переживает перезапуск (`state.json`), стартует с битым конфигом, пишет лог с ротацией, стартует без предварительной уборки (маршруты и ключ DNS синхронизируются с новым состоянием, а не снимаются заранее). CLI получает `wgplex check`. `config.apply` заменяется на `config.reload`.

Правила — design 4.1, 5, 6, 7.2, 8, 10, 11, 13 (частично), 15, 21.1 (M2); CLAUDE.md. Объём этапа — по design 21.1 (M2 «Системный режим»), не только уборка при старте.

## Контекст

Состояние после M1 (план `m1-port.md`, решения 3–8, «Ход работы»):

- конфиг доставляет клиент: CLI читает каталог и отправляет файлы методом `config.apply` (`cmd/wgplex/main.go:88`, `internal/rpc/server.go:63`) — как в Wirefork;
- RPC — только root: `allow` = `uid == 0` (`cmd/wgplex/daemon_main.go:151`);
- переключатели туннелей — только в памяти, первое применение — по `autostart` (решение 3 плана M1);
- логи — только stderr; `-log`, pid-файл, SIGUSR1 удалены (решение 8);
- при старте демон снимает наследство явно: `router.DeleteOwned()` + `releaseDNS()` (`cmd/wgplex/daemon_main.go:69-72`) — решение 7 плана M1, «как в Wirefork до M2»;
- DNS — как в Wirefork до M4: резолвер `127.0.0.1:53` (`cmd/wgplex/daemon.go:31`), захват `SupplementalMatchDomains = [""]` через `scutil` (`internal/dns/sysdns.go:101`), UUID уже свой.

Пробел: `docs/api.md` требуется `CLAUDE.md` («Источник истины»), файла нет ни здесь, ни в `wgplex-app` (репозитория локально нет — пробел зафиксирован). Полный контракт API — этап M3 (design 21.1); на M2 — минимальный каркас по текущему коду (решение пользователя, отклонение от 21.1 закрывается в M3).

## Поведение

Что изменится для пользователя и внешних систем (устройство — design 10, 11, 13, 15):

- **Демон читает конфиг сам** (design 10.2): при старте и по `config.reload` — каталог `<prefix>/etc/wgplex` (по умолчанию; флаг `-config` демона — для отладки). `wgplex reload` — только триггер, без `-config` и без отправки файлов; `config.apply` и `ApplyParams` удаляются.
- **Права и владельцы файлов** (design 5): владелец каталога — по `stat` при каждой проверке; каталог и каждый читаемый файл принадлежат root или владельцу каталога и не записываемы для группы/остальных — иначе ошибка конфига; `.conf`, читаемый группой/остальными, — предупреждение; TCC-подсказка в тексте ошибки при `EPERM` (симлинк в `~/Documents` и т.п.); читаются только `wgplex.yaml` и `.conf`, на которые ссылаются туннели, обычные файлы до 1 МБ; симлинки допускаются.
- **Переключатели в `state.json`** (design 11): `<prefix>/var/wgplex/state.json`, туннели, включённые/выключенные явно, и их состояние; без записи — `autostart`; атомарная запись (tmp + rename); битый файл — предупреждение, туннели по `autostart`; туннели, которых нет в конфиге, из state.json убираются при каждом удачном применении. Пауза и снимок блокировки — не в M2 (design 21.1: M3).
- **Старт с битым конфигом** (design 4.1, 10.2): демон работает без туннелей, `configured: false`, ошибки — в `config_errors` (`status.get`) и лог; без снимка блокировки (M3). Каталога нет — ошибка «нет каталога». Пустой конфиг — `configured: true`, туннелей нет.
- **`wgplex check`** (design 13): локальная проверка конфига без демона и root, `-config dir`; вывод — текст (собираются все ошибки и предупреждения); `-json` — M3 вместе с API.
- **Логи с ротацией** (design 15): демон пишет `<prefix>/var/log/wgplex/wgplex.log` и подменяет им stdout/stderr (`dup2` на fd 1 и 2); ротация на 5 МБ → `.1` (старый `.1` → `.2`, `.2` удаляется); файл и архивы `0640`, владелец root, группа `admin` (группа `control_group` — M3); имена из DNS-запросов — только на debug (`-v`). Флаги демона: `-config`, `-socket`, `-state`, `-log` (design 13, решение 11 плана M1).
- **Старт без предварительной уборки** (design 4.1, 6, 7.2): `router.DeleteOwned()` и `releaseDNS()` при старте удаляются; демон сразу синхронизирует таблицу маршрутов и ключ захвата DNS с новым состоянием — лишнее уходит при синхронизации, ключ переиздаётся по зонам нового конфига (снятие — когда зон нет и при остановке). Мотивация полная (непрерывность `fallback: block`, 9.1) — с M3, когда появится снимок блокировки.
- **Каркас `docs/api.md`** (на английском): минимальное описание текущего контракта — сокет, `POST /rpc`, методы после замены (`status.get`, `diag.explain`, `diag.routes`, `config.reload`, `tunnel.setEnabled`, `tunnel.disableAll`), коды ошибок `1`–`4` (сверено с `internal/rpc/rpc.go`; `5` — planned, M3), доступ до M3 — root (HTTP 403 до метода). Пометка «in progress, full contract with M3».

## Границы и инварианты

- **Не в M2** (design 21.1): права по методам и `control_group`, `mbr_check_membership`, урезанные ответы, ошибка `5`, `tunnel.enable/disable` и `down -all`, пауза, снимок блокировки, `-json`, код выхода `3`, точечный захват DNS по зонам (M4), возврат на приоритетный туннель (M5), `docs/api.md` в полном объёме (M3). До M3 — `allow` = `uid == 0`.
- Поведение ядра (туннели, маршруты, резолвер, здоровье) не меняется — кроме стартовой уборки (задача Г).
- Ключи не попадают в логи, ответы API и фикстуры (CLAUDE.md).
- Свои метки не трогаются: `RTF_PROTO2`, свой UUID захвата.
- Root и система (CLAUDE.md): на хосте — без `sudo` и без изменений сети; всё системное — в VM через `scripts/vm.sh`, клоны `wgp-check-*` образа `wgp-base`, bridged-сеть.
- `make check` зелёный перед каждым коммитом; коммиты — Conventional Commits без Co-Authored-By (сессия OpenCode, AGENTS.md).
- Правки `design.md` — только если реализация вскроет расхождение; согласование с пользователем до коммита. Каркас `api.md` — согласован этой спекой.

## Проверка

Unit-сценарии (дано/когда/то; тесты `test-dev` + существующие):

1. Дано: каталог, где `wgplex.yaml` записываем для группы; когда разбор; то ошибка конфига, собираются и остальные ошибки (не только первая).
2. Дано: `.conf` читаемый группой; когда разбор; то предупреждение, конфиг применяется.
3. Дано: ошибка чтения с `EPERM`; когда разбор; то текст называет TCC и советует перенести файл.
4. Дано: `state.json` с записью `t1: on`; когда старт с конфигом, где `t1` есть и `autostart: false`; то `t1` включён. Когда конфиг без `t1`; то запись убрана.
5. Дано: битый `state.json`; когда старт; то предупреждение, туннели по `autostart`.
6. Дано: YAML с двумя ошибками; когда `wgplex check`; то обе показаны, код 1; на хорошем конфиге — код 0.
7. Дано: лог 5 МБ + существующие `.1`; когда порог превышен; то `.1` → `.2`, новый файл открылся, запись продолжается (в т.ч. после `dup2`).

Проверка в VM (оркестратор, `scripts/vm.sh`, клоны `wgp-check-m2-*` образа `wgp-base`, мост):

- Стенд: вторая VM — WireGuard-сервер (design 21.1 M2); конфиг демона — туннель к стенду.
- LaunchDaemon — временный plist через `vm.sh` (формулы ещё нет); каталоги `/opt/homebrew/var/run`, `/opt/homebrew/etc/wgplex`, `/opt/homebrew/var/wgplex`, `/opt/homebrew/var/log/wgplex` — шагом проверки.
- 1. Дано: LaunchDaemon установлен; когда VM перезагружена без входа пользователя; то демон работает, туннель к стенду поднят, handshake есть (главный критерий этапа).
- 2. Дано: конфиг с ошибкой; когда демон стартует; то демон жив, `status` — `configured: false`, ошибки показаны, туннелей нет.
- 3. Дано: упавший демон оставил маршруты `RTF_PROTO2` и ключ DNS от старого конфига; когда демон стартует с новым конфигом; то лишнее уходит при первой синхронизации (до старта — не снималось), ключ переиздан по зонам; `wgplex check` — без демона, от обычного пользователя.
- 4. Дано: `wgplex up t1` от root, перезапуск демона; то `t1` снова поднят (переключатель из `state.json`), при `down t1` и перезапуске — не поднят.
- 5. Файл лога пишется, права `0640`, ротация наблюдается (заполнение). `SIGHUP`/`SIGUSR1` — демон жив; `SIGTERM` — маршруты и ключ сняты, код 0.

wgp-check-* клоны сносятся после проверок (см. «Уборка»).

## Риски

- **Объём:** M2 по 21.1 шире, чем «уборка при старте» (вопреки первоначальной постановке); внутри ветки этапа задачи А–Д идут волнами, слияние — одно, в конце этапа.
- **Перезагрузка без входа в VM:** зависит от настроек `wgp-base` (автологин должен быть выключен, FileVault — выключен); проверить до задачи Г.
- **Стенд — новая инфраструктура:** WireGuard-сервер во второй VM создаётся впервые; время на отладку стенда не в коде.
- **Отказ от стартовой уборки** опирается на доворачивающую синхронизацию (7.2); регресс = утечка stale-маршрутов/ключа. Закрывается сценарием 3 проверки в VM.
- **`dup2` и ротация:** паники Go должны попадать в актуальный файл; тонкое место, покрыть unit-тестом.
- **`config.reload` — несовместимая смена контракта** относительно `config.apply`: каркас `api.md` фиксирует новое имя сразу, чтобы `wgplex-app` (A1, после M3) не наследовал старое.
- Пользователь выполняет: подтверждение плана, наблюдение за VM-проверкой (шаги с root в VM — агентом через `vm.sh`), подтверждение результата перед слиянием.
