# M3 — имена RPC-методов (внеочередной шаг)

> Статус: done · Владелец: оркестратор · Ревью: блокеров нет, замечания исправлены
> Ручная проверка не требуется: меняется только контракт, системного поведения нет

**Цель:** привести работающий RPC к правилу design 14 — `объект.глагол`, без булевых параметров: `tunnel.setEnabled {name, enabled}` заменяется на `tunnel.enable {name}` и `tunnel.disable {name}`, алиас не остаётся.

Шаг согласован пользователем вне очереди M3 (2026-10-21) после вопроса о том, сохранилось ли решение о глаголах в документации. Решение было в design 14, но `docs/api.md` описывал transitional-метод как актуальный контракт.

## Контекст

- Design 14 (строки 506–518): методы `tunnel.enable`/`tunnel.disable` с `{name}`; «Правило имён — `объект.глагол`, без булевых параметров».
- Планы M1/M2 прямо откладывали rename до M3: методы были перенесены из Wirefork как есть (`tunnel.setEnabled`), чтобы не менять контракт во время переноса.
- `docs/api.md` (скелет после M2) перечислял `tunnel.setEnabled` и относил rename к «planned M3».
- `wgplex-app` ещё не начат (A1 — после M3), поэтому ломать клиентов некому.

## Поведение

- `tunnel.enable {name}` — включает туннель; повтор идемпотентен, на туннеле в состоянии `error` повторяет подъём. Ошибки: `2` (конфиг не применён), `3` (неизвестный туннель), `4` (не поднялся), `-32602` на пустое имя.
- `tunnel.disable {name}` — выключает туннель; повтор идемпотентен. Ошибки: `2`, `3`, `-32602`; кода `4` нет — ничего не поднимается.
- Оба пишут переключатель в `state.json` (design 11).
- CLI: `wgplex up` → `tunnel.enable`, `wgplex down` → `tunnel.disable`.
- `tunnel.setEnabled` не зарегистрирован: ответ `-32601` (Method not found), демон не вызывается.
- Внутренний `daemon.SetEnabled(name, enabled)` сохранён как общая реализация двух методов; bool остаётся только внутри, в контракт не попадает.

## Шаги

1. Ветка `m3-api-naming` от `master`.
2. Типы RPC: `SetEnabledParams` → `TunnelParams {name}`; сервер регистрирует `tunnel.enable`/`tunnel.disable` через общий `toggle`.
3. CLI `up`/`down` — новые методы.
4. Тесты сервера: обе стороны, коды ошибок для каждого метода, пустое имя и неверные типы, отсутствие `tunnel.setEnabled` (`-32601`).
5. `docs/api.md` — новые методы, коды ошибок, раздел Limitations без обещания rename; `docs/design.md` 21.1 — выполненный пункт снят с M3.
6. Комментарии в коде (`internal/rpc`, `internal/state`, `cmd/wgplex`) приведены к новым именам.
7. `make check`; ревью диффа отдельным агентом; исправление замечаний.

## Границы и инварианты

- Не меняются: права доступа (до M3 — только root), коды `1`–`5`, поля `status.get`, поведение туннелей и маршрутов, `tunnel.disableAll`.
- Алиас `tunnel.setEnabled` не оставляется — ни «на время», ни для совместимости: клиентов ещё нет.
- Исторические планы M1/M2 не правятся — там `tunnel.setEnabled` отражает состояние на момент этапа.
- Правки `api.md`/`design.md` — в этой же ветке.

## Проверка

- `make check` (gofmt + vet + tests) — зелёный.
- Тесты сервера покрывают оба метода и отрицательный кейс снятого имени.
- Ревью: соответствие design 14 и `api.md`, коды ошибок, идемпотентность, остатки старого имени. Блокеров нет; замечания 1–3, 5 исправлены (таблица кейсов читает `enabled`, ошибки проверяются для обоих методов, добавлен тест `-32601`, уточнён статус `api.md`).
- Ручная проверка в VM не нужна: системные вызовы и сеть не затронуты.
