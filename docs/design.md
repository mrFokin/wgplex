# wgplex — документ проектирования (черновик)

Статус: черновик, 2026-10-20. Собран по обсуждению; разделы «как в Wirefork» переносятся целиком на M1.

wgplex — отдельный продукт на основе кода Wirefork. Ядро (туннели, маршрутизация, DNS, здоровье) переносится копией и дальше развивается независимо. Разделы с пометкой «как в Wirefork» ссылаются на `wirefork/docs/design.md` в состоянии ветки `m11-reliability` (2026-10-20); перед согласованием их текст переносится сюда целиком с перечисленными отличиями.

## 1. Задача

Несколько WireGuard-туннелей одновременно на macOS с раскладкой трафика по правилам — как Wirefork, но в другой модели владения:

| | Wirefork | wgplex |
|---|---|---|
| Машины | Mac с несколькими пользователями, у каждого свои туннели | Mac одного человека или общий набор туннелей на машину |
| Чьи туннели | пользователя за консолью | машины |
| Когда поднимаются | при входе пользователя | при загрузке |
| Выход и смена пользователя | сброс | ничего не меняется |
| Конфиг | у каждого пользователя, присылает приложение | один на машину, демон читает сам |
| Установка | `.pkg` | Homebrew |

Опорный сценарий — как в Wirefork (рабочий и домашний туннели, сервисы через nl с резервом de), плюс:

- админ ставит и настраивает wgplex через brew, работает в CLI;
- остальные пользователи машины видят статус и, если им разрешено, переключают туннели из меню `Wgplex.app`.

## 2. Рамки

**Платформа:** macOS 13 Ventura и новее, Apple Silicon и Intel. Linux не поддерживается: системный слой (utun, `PF_ROUTE`, SCDynamicStore) — только darwin.

**Аудитория:** публичный open-source проект. Админы — CLI через brew; пользователи «попроще» — приложение.

**Состав:**

- `wgplex` — движок: демон и CLI в одном бинарнике, репозиторий `mrFokin/wgplex`, формула `wgplex` в tap `mrFokin/homebrew-tap`;
- `Wgplex.app` — меню в строке состояния и окно, репозиторий `mrFokin/wgplex-app`, `.dmg` в релизах и cask `wgplex-app` (раздел 17).

Движок ничего не знает о приложении: приложение — один из клиентов публичного API (раздел 14).

**Не входит в v1** — раздел 19.

## 3. Имена и пути

`<prefix>` — `HOMEBREW_PREFIX`; все пути по умолчанию выводятся из него, флаги нужны только для отладки. Бинарник готовый и universal (16), поэтому prefix определяется при запуске:

1. путь к исполняемому файлу без симлинков содержит `/Cellar/` — prefix — всё до `/Cellar/` (установка через brew, в том числе в нестандартный prefix);
2. иначе — по архитектуре процесса: `/opt/homebrew` на arm64, `/usr/local` на x86_64 (сборка для разработки, `make build`).

| Что | Значение |
|---|---|
| Продукт | wgplex |
| Go-модуль | `github.com/mrFokin/wgplex` |
| Бинарник | `<prefix>/bin/wgplex` |
| Конфиг | `<prefix>/etc/wgplex/wgplex.yaml` + `*.conf` рядом (симлинки допускаются) |
| Сокет | `<prefix>/var/run/wgplex.sock` |
| Состояние | `<prefix>/var/wgplex/state.json` |
| Лог | `<prefix>/var/log/wgplex/wgplex.log` (+ архивы, раздел 15) |
| Сервис | `sudo brew services start --sudo-service-user=root wgplex` (LaunchDaemon `sh.brew.wgplex`, plist `/Library/LaunchDaemons/sh.brew.wgplex.plist` генерирует brew, 16.4) |
| Приложение | `/Applications/Wgplex.app`, bundle id `io.github.mrfokin.wgplex` |

## 4. Архитектура

```
┌──────────────────┐   ┌──────────────┐
│  Wgplex.app      │   │  wgplex      │      любой пользователь
│  (меню + окно)   │   │  (CLI)       │
└────────┬─────────┘   └──────┬───────┘
         │  JSON-RPC 2.0 / HTTP / unix socket <prefix>/var/run/wgplex.sock
─────────┼────────────────────┼──────────────────────────────────────────
┌────────┴────────────────────┴───────────────────────────┐ root
│ wgplex daemon (LaunchDaemon через brew services)        │
│  ├─ config    читает <prefix>/etc/wgplex сам            │
│  ├─ tunnels   wireguard-go, utun на туннель             │
│  ├─ router    расчёт таблицы маршрутов, синхронизация   │
│  ├─ dns       резолвер для доменов из правил            │
│  ├─ health    handshake, ping, HTTP; failover           │
│  ├─ netwatch  смена сети, сон/пробуждение               │
│  ├─ state     переключатели и пауза                     │
│  └─ rpc       mrFokin/jrpc/v2                           │
└─────────────────────────────────────────────────────────┘
```

### 4.1. Демон

- `wgplex daemon` запускается launchd при загрузке, работает от root, перезапускается при падении (`KeepAlive`, кроме выхода с кодом 0).
- Запущен не от root (`brew services start` без `sudo` ставит копию как LaunchAgent пользователя, M0, H7) — ошибка в лог и выход с кодом 0: launchd его не перезапускает (16.4).
- Каталоги `var/wgplex` и `var/log/wgplex` создаёт формула (10.3); демон создаёт только недостающее внутри них. Родителей (`var`, `var/log`) не создаёт: созданный root `var/log` ломает brew пользователю (M0, H6).
- Со старта читает конфиг и поднимает туннели по состоянию (11) — вход пользователя не нужен.
- Не следит за пользователем за консолью: ни сброса при выходе, ни переключателей на пользователя.
- Конфиг с ошибками при старте — демон работает без туннелей, ошибка в `status.get`; не падает (иначе `KeepAlive` гонял бы перезапуски).
- Свои метки, отличные от Wirefork: маршруты помечаются `RTF_PROTO2` (у Wirefork — `RTF_PROTO1`; `RTF_PROTO3` занят ядром, `RTPRF_OURS` в `net/route.h`), у синтетического DNS-сервиса (8) — свой постоянный UUID. Демон удаляет и заменяет только маршруты со своим флагом, поэтому маршруты Wirefork или другой копии кода для него чужие (6.2 Wirefork: не трогаются, предупреждение в лог). Отдельной проверки на Wirefork нет.

### 4.2. CLI

Тот же бинарник, клиент того же API, что и приложение (раздел 13). Исключение — `wgplex check`: проверяет конфиг локально, без демона и root.

### 4.3. Приложение

Отдельный продукт поверх API (раздел 17).

## 5. Модель угроз и доступ

**Владелец prefix brew — доверенный, фактически равен root:** ему принадлежит бинарник, который root запускает как демон. Защищаться от него бессмысленно. Защищаемся только от **других** пользователей машины.

Следствия:

- демон (root) читает файлы из каталога конфига владельца; симлинки допускаются;
- запись в каталог конфига и его файлы группе или остальным — ошибка конфига: посторонний мог бы перенаправить трафик (проверяется по цели симлинка);
- `.conf`, доступный на чтение группе или остальным, — предупреждение (как у `wg-quick`);
- сокет `0666`, права — по методам:

| Методы | Кто |
|---|---|
| `status.get`, `diag.*` | все |
| изменяющие (`config.reload`, `tunnel.*`, `daemon.*`) | root, владелец каталога конфига, члены `control_group` |

- uid соединения — `LOCAL_PEERCRED`. Группы из `LOCAL_PEERCRED` не используются: их не больше 16, а у администратора macOS их часто больше. Членство проверяется через Directory Services вызовом `mbr_check_membership` (cgo, `membership.h`; uid и имя группы → UUID через `mbr_uid_to_uuid` и `mbr_identifier_to_uuid`), только для изменяющих методов. Учитывает вложенные группы, изменения членства видны сразу, 0,1–2 мс, root не нужен (M0, G1, G5, G7). `dsmemberutil` не используется: код выхода у «член» и «не член» одинаковый (M0, G2).
- `control_group` задаётся именем: несуществующая группа находится при поиске имени (`ENOENT`) и становится ошибкой конфига; у числового gid она неотличима от «не член».
- `control_group` — в `wgplex.yaml`, по умолчанию `admin`. Несуществующая группа — ошибка конфига; пока конфиг не применён, управляют только root и владелец.
- Ключи не попадают в логи и ответы API (как в Wirefork 9.4).

## 8. DNS

Как в Wirefork, раздел 7, кроме захвата.

**Точечный захват.** Синтетический сервис `State:/Network/Service/<постоянный UUID wgplex>/DNS` (свой, не Wirefork, 4.1) публикует не `SupplementalMatchDomains = [""]` (все имена), а только нужные зоны:

- домены сервисов из всех правил (`=example.com` — зона `example.com`);
- `dns_domains` туннелей.

Ключ сервиса (M0, D1–D7, D11):

| Поле | Значение |
|---|---|
| `ServerAddresses` | `[127.0.0.1]` |
| `ServerPort` | порт резолвера (ниже) |
| `SupplementalMatchDomains` | зоны |
| `SupplementalMatchOrders` | для каждой зоны — `1`: при той же зоне у чужого VPN выигрывает wgplex (без явного порядка победитель случаен) |
| `SupplementalMatchDomainsNoSearch` | `1`: иначе все зоны попадают в search list, короткие имена и каждый сброс кэша дают сотни запросов |

- Других ключей (`Setup:`, `State:/Network/Global/DNS`) не нужно.
- Запись — через SystemConfiguration (`SCDynamicStoreSetValue`, cgo), не `scutil`: `scutil` принимает не больше 99 значений поля и молча обрезает длинные строки (M0, D2). Запись 500 зон — 10–15 мс, ответы по новым зонам — через ~0,1 с.
- **Лимит — 1000 зон**, больше — ошибка конфига. Около 4000 зон система молча оставляет прежнюю DNS-конфигурацию (предел зависит от длины имён, M0, D9). После записи демон проверяет по `dnsinfo`, что резолверы для зон появились; нет — ошибка в `status.get` и лог.
- Конкретная зона выигрывает у `[""]` чужого VPN при любом порядке публикации: решает самый длинный суффикс (M0, D5). Более длинная зона чужого сервиса (`www.example.com` против нашей `example.com`) забирает свои имена — ограничение (18).
- Резолвер отвечает на любые типы запросов, в том числе `SVCB _dns.resolver.arpa` (DDR от mDNSResponder, M0, D12).

Остальные имена mDNSResponder резолвит сам, мимо демона. Следствия:

- сбой или перезапуск демона ломает только имена из правил, а не весь DNS машины: они не резолвятся около 60 с (к исходному DNS сами не уходят, M0, D10), остальные работают. Поэтому при остановке демон снимает ключ первым делом — это сразу освобождает и зависшие запросы;
- конкретный supplemental-домен точнее `[""]` чужого VPN — имена из правил работают и рядом с ним (в Wirefork они шли мимо);
- в резолвер приходят и поддомены зон, которым правило не подходит (`mail.google.com` при `=google.com`), и имена правил в `fallback: default` — они уходят исходным DNS системы, как в Wirefork;
- захват — если список зон не пуст; меняется при `config.reload`.

**Адрес резолвера** — `127.0.0.1` на нестандартном порту (ключ `ServerPort`), порт — константа. `127.0.0.1:53` часто занят: dnsmasq (в том числе Laravel Valet для `*.test`), sing-box, dnscrypt-proxy, unbound, AdGuard Home. На своём порту wgplex работает рядом с ними: благодаря точечному захвату имена из правил идут в wgplex, остальные — тому, кто на `:53`. `ServerPort` у supplemental-резолвера работает (M0, D3); вид `127.0.0.1.<порт>` в `ServerAddresses` — нет (D11).

**Порт занят** — демон не падает (иначе `KeepAlive` гонял бы перезапуски): работает без правил по доменам (динамических адресов и захвата нет, CIDR-правила работают), ошибка — в `status.get` и в лог; повтор — при `config.reload`.

## 9. Здоровье и failover

Как в Wirefork, раздел 8 (пассивная проверка, `check` — ping или HTTP, мёртвый туннель исключается из `via`, `fallback: default | block`, защита от утечек), с отличием:

**Возврат на приоритетный туннель.** Правило, ушедшее на резерв, возвращается на более приоритетный туннель из `via`, когда тот жив 5 минут подряд (константа). Возврат рвёт открытые соединения один раз. В Wirefork возврата нет: там пользователь видит иконку и переключит сам; headless-демон мог бы неделями работать на резерве после короткого сбоя.

## 10. Конфигурация

### 10.1. Формат

Как в Wirefork 9.1–9.2 и 9.4: главный файл `wgplex.yaml`, `.conf` рядом, та же схема и валидация. Конфиг Wirefork переносится копированием (с переименованием файла). Новое поле верхнего уровня:

```yaml
control_group: admin   # кто, кроме root и владельца, управляет (5)
```

Остальные `*.yaml` в каталоге игнорируются с предупреждением.

### 10.2. Применение

- Демон читает каталог сам: при старте и по `config.reload` (`wgplex reload`, «Перечитать» в окне). За изменением файлов не следит; SIGHUP не перечитывает.
- Повторное применение — как в Wirefork 9.3: работающий туннель перезапускается, только если изменился его `.conf`; изменения YAML — без перезапуска туннелей; выбор туннелей для правил — заново.
- Ошибка при `reload` — конфиг не применяется, работает прежний; ошибки — в результате и в `status.get`.
- Ошибка при старте — туннелей нет (`configured: false`, `config_errors`). Копия последнего удачного конфига не хранится: это ещё одно место с ключами и поведение «работает не то, что в файле».
- Каталога нет — ошибка конфига «нет каталога».

### 10.3. Шаблон

Формула в `post_install_steps` (`post_install` в Homebrew 7 устарел, M0, H2, H18) создаёт каталог (`0700`) и `wgplex.yaml` (`0600`) из шаблона, если каталога нет (`unless_path_exists`), а также `var/wgplex` и `var/log/wgplex` (4.1). Шаблон целиком закомментирован (пустой конфиг валиден: туннелей нет, DNS не захватывается): что положить в каталог и пример 9.1 Wirefork. Обновление формулы существующий каталог не трогает.

## 11. Состояние

`<prefix>/var/wgplex/state.json`, одна запись на машину:

- **переключатели** — туннели, которые включали или выключали явно (`tunnel.enable`, `tunnel.disable`, `tunnel.disableAll`), и их состояние. Туннель без записи — по `autostart`. Успешный `config.reload` убирает туннели, которых нет в конфиге;
- **пауза** — `paused`.

Запись атомарная (временный файл в том же каталоге и `rename`). Файл не читается или битый — предупреждение в лог, туннели по `autostart`, без паузы.

Не сохраняется: на каком туннеле сейчас правило, вердикты здоровья, динамические адреса. После перезапуска правила начинают с первого туннеля `via`, адреса появляются по DNS-запросам.

## 12. Пауза и «Выключить все»

| | Пауза | Выключить все |
|---|---|---|
| Смысл | временно: как Mute, поверх переключателей | постоянно: снимает переключатели |
| Переключатели туннелей | не меняются | все — выключены |
| Возврат | «Возобновить» — поднимается прежний набор | включать туннели по одному |
| Переживает перезапуск | да | да |
| CLI | `wgplex pause` / `wgplex resume` | `wgplex down -all` |
| Меню | «Приостановить» / «Возобновить» | нет (окно) |

- На паузе туннели опущены, `tunnel.enable`/`disable` меняют переключатели, но ничего не поднимают.
- Правила в паузе и после «Выключить все» уходят в fallback; `fallback: block` продолжает блокировать (как «Выключить все» в Wirefork): обычный пользователь не может обойти запрет админа паузой. Захват DNS остаётся, если правилам есть что блокировать.
- Пауза общая для всех пользователей, право — как у остальных изменяющих методов.

## 13. CLI

```
wgplex status [-json]            туннели, handshake, трафик, проверки, правила
wgplex explain <домен|IP> [-json] какое правило, какой туннель и почему
wgplex routes [-json]            текущие маршруты: из конфига и динамические
wgplex up <туннель>              включить (запоминается)
wgplex down <туннель> | -all     выключить один или все (запоминается)
wgplex pause | resume            пауза (12)
wgplex reload                    демон перечитывает конфиг
wgplex check [-config dir] [-json] проверить конфиг без демона и root
wgplex daemon [-v]               демон (из brew services)
wgplex version
```

- Вывод — текст; `-json` у команд только для чтения и `check` — те же структуры, что в API.
- `wgplex status` отмечает правила на резерве и в fallback, паузу; колонка `CHECK` — как в Wirefork 12.
- Коды выхода: `0` — успех, `1` — ошибка (в том числе нет прав), `2` — неверные аргументы, `3` — демон недоступен (нет сокета, отказ, таймаут).
- Нет прав — `permission denied: up/down/reload require root, the config owner or membership in group "<группа>"`.
- Отладочные флаги: `-socket` у клиентских команд; `-config`, `-socket`, `-state`, `-log` у `daemon`.
- Тексты CLI и демона — на английском.

## 14. API

JSON-RPC 2.0 на `github.com/mrFokin/jrpc/v2` (Echo v5), HTTP поверх unix-сокета, `POST /rpc`; сокет и проверка `LOCAL_PEERCRED` — как в Wirefork 13. Push-уведомлений нет, только опрос. Публичный контракт — `docs/api.md` (английский).

| Метод | Параметры | Права | CLI |
|---|---|---|---|
| `status.get` | — | все | `status` |
| `diag.explain` | `{query}` | все | `explain` |
| `diag.routes` | — | все | `routes` |
| `config.reload` | — | управление | `reload` |
| `tunnel.enable` | `{name}` | управление | `up` |
| `tunnel.disable` | `{name}` | управление | `down` |
| `tunnel.disableAll` | — | управление | `down -all` |
| `daemon.pause` | — | управление | `pause` |
| `daemon.resume` | — | управление | `resume` |

- Правило имён — `объект.глагол`, без булевых параметров. Изменяющие методы идемпотентны.
- `status.get` — как в Wirefork, плюс: `api_version` (целое, сейчас `1`), `version` (движка), `can_control` (для вызывающего), `control_group`, `paused`, `config_dir`, `log_path`; `icon` — `off | on | warn | paused`. `configured: false` с `config_errors` — «запущен без туннелей».
- `config.reload` — результат и ошибки как у `config.apply` Wirefork.
- Ошибки: `1` — конфиг не прошёл проверку (`data`: ошибки и предупреждения), `2` — конфиг не применён, `3` — неизвестный туннель, `4` — туннель не поднялся, **`5` — нет прав** (`data`: `control_group`). Отказ в правах — ошибка JSON-RPC, не HTTP 403: чтение доступно всем.
- **Совместимость:** в пределах `api_version` поля и методы только добавляются, клиент игнорирует незнакомые поля. Несовместимое изменение — следующая `api_version`.

## 15. Логи

- `log/slog`; демон сам пишет `<prefix>/var/log/wgplex/wgplex.log` и подменяет им stderr (`dup2` на fd 2 — туда попадают и паники Go).
- До `dup2` stderr и stdout — тот же файл через `log_path`/`error_log_path` формулы (16.4): без них launchd отдаёт `/dev/null`, и ранние ошибки теряются (M0, H5).
- Ротация в демоне: при 5 МБ файл переименовывается в `wgplex.log.1` (старый `.1` — в `.2`, `.2` удаляется), открывается новый. newsyslog, pid-файл и SIGUSR1 не нужны.
- Файл `0644`: его читает окно приложения у любого пользователя. Имена из DNS-запросов — только на уровне debug (`-v`), как в Wirefork.

### 16.2. Сборка

- `make check` — `gofmt -l` (пусто), `go vet ./...`, `go test ./...`.
- Сборка с cgo (`CGO_ENABLED=1`: SystemConfiguration для DNS, `membership.h` для прав, 5 и 8) — нужны Command Line Tools; срез `amd64` — `CC="clang -arch x86_64"`. У пользователя бинарник готовый (16.4).
- `make build` — `build/wgplex`: `GOARCH=arm64` и `amd64`, склейка `lipo -create`, ad-hoc подпись (`codesign --sign -`: линкер подписывает только срез arm64), версия — `-ldflags -X main.version=…`. Запуск для разработки: `sudo ./build/wgplex daemon` (пути — по архитектуре, 3).
- `make release` — `make check`, `make build`, архив `wgplex-X.Y.Z-darwin-universal.tar.gz`, sha256.

### 16.3. Релиз (вручную, пока нет CI)

1. Поднять версию, `make release`, тег, `gh release create` с архивом.
2. В tap — новые `url`, `sha256`, `version` формулы, коммит.
3. Проверка: `brew upgrade wgplex`, `sudo brew services restart --sudo-service-user=root wgplex`, `brew list --versions wgplex` — одна версия, `brew test wgplex`, `wgplex version`.

### 16.4. Формула

- `wgplex` в `mrFokin/homebrew-tap` (`brew install mrfokin/tap/wgplex`): **готовый universal-бинарник** из релиза, Go у пользователя не нужен, установка — секунды. Так принято в собственных tap (например, `hashicorp/tap`); собрать самому — `make build` из репозитория. Формулы карантин не получают, Gatekeeper бинарник не проверяет. `depends_on :macos`.
- Установка — только по полному имени `brew install mrfokin/tap/wgplex`: Homebrew 7 загружает формулы стороннего tap только при доверии, полное имя доверяет сам (иначе — `brew trust mrfokin/tap`, M0, H1).
- `service do`: `run [opt_bin/"wgplex", "daemon"]`, `require_root true`, `keep_alive successful_exit: false` (4.1), `log_path` и `error_log_path` — `var/"log/wgplex/wgplex.log"` (15).
- **Запуск — `sudo brew services start --sudo-service-user=root wgplex`.** Без `--sudo-service-user=root` brew делает root владельцем бинарника и симлинков формулы, после чего `brew upgrade`, `cleanup` и `uninstall` от пользователя оставляют мусор или падают (M0, H3, H8–H13); с опцией владельцы не меняются, демон всё равно root (H16). Защиты бинарника от владельца prefix это не убирает — её нет и так (5). Опция нужна при каждом `start` и `restart`.
- **`brew upgrade` службу не перезапускает** (M0, H8): новая версия — после `sudo brew services restart --sudo-service-user=root wgplex`.
- `brew services` без `sudo` управляет не службой root, а копией от пользователя (M0, H7).
- `caveats`: команда запуска с `--sudo-service-user=root` (строка, которую brew добавляет сам, — без опции), перезапуск после `upgrade`, `brew services` только через `sudo`; где конфиг; что root запускает бинарник из prefix владельца (5).
- `test do`: `wgplex version`, `wgplex check` на шаблоне.
- Удаление — строго в этом порядке: `sudo brew services stop wgplex` (выгружает службу и удаляет plist), затем `brew uninstall wgplex`. Наоборот — plist остаётся, а `brew services` его уже не видит: `uninstall` снимает доверие к формуле (M0, H17). Каталог конфига остаётся (`etc` brew не удаляет), `var/wgplex` и `var/log/wgplex` — тоже (файлы root, `sudo rm`). При остановке демон снимает маршруты и захват DNS (как в Wirefork).
- CI — вне v1.

## 17. Приложение Wgplex.app

Отдельный репозиторий `mrFokin/wgplex-app`; раздел переносится туда при его создании.

### 17.1. Поставка

- **Основной канал — cask `wgplex-app`** в `mrFokin/homebrew-tap`: `depends_on formula: "mrfokin/tap/wgplex"`, `depends_on macos: ">= :ventura"`, `.dmg` из релиза GitHub. Запасной — тот же `.dmg` вручную (universal, ad-hoc подпись).
- Установка: `brew trust mrfokin/tap`, затем `brew install --cask mrfokin/tap/wgplex-app`. Homebrew 7 доверяет по полному имени только самому cask, а формулу-зависимость из того же tap без `brew trust` не загружает (M0, K4, K11).
- Developer ID пока нет. Первый запуск (M0, K6, K7): диалог «"Wgplex" Not Opened — Apple could not verify…», кнопка «Done» (не «Move to Trash»); затем «Системные настройки → Конфиденциальность и безопасность» → «"Wgplex" was blocked to protect your Mac» → «Open Anyway» → пароль администратора. Тексты — в README. С подписью меняется только этап сборки.
- **Обновление через `brew upgrade --cask` повторного разрешения не требует:** Homebrew сохраняет каталог `.app` и переносит одобрение (M0, K8, K9). Ручная замена из `.dmg` — требует «Open Anyway» снова (K10).
- Обновления: раз в сутки запрос последнего релиза через GitHub API (если включено «Проверять обновления»). Новая версия — одно уведомление на версию (17.6) и баннер в окне до обновления: команда `brew upgrade --cask wgplex-app` с копированием и ссылка на страницу релиза. Sparkle не используется.

### 17.2. Движок

- Сокет ищется по `/opt/homebrew/var/run/wgplex.sock`, затем `/usr/local/var/run/wgplex.sock`; переопределение — в настройках.
- Три состояния без движка: сокета нет — «wgplex не установлен», «Как установить…»; сокет не отвечает — «Демон не запущен», команда `sudo brew services start --sudo-service-user=root wgplex` с копированием; `api_version` меньше нужной — «Обновите wgplex»: `brew upgrade wgplex` и `sudo brew services restart --sudo-service-user=root wgplex`.
- «Выход» закрывает только приложение: туннели принадлежат машине. Остановка демона — `brew services`, не GUI.

### 17.3. Меню

`NSStatusItem` + `NSMenu` (AppKit): свежий `status.get` при открытии (`menuNeedsUpdate`), обновление раз в 1–2 с, пока меню открыто (таймер в `.common` mode); в фоне — раз в 10 с для иконки.

```
✓ nl
✓ de  ⚠
  work
──────────
⚠ youtube на резерве        (только когда есть проблема)
──────────
Приостановить               (на паузе — «Возобновить», галочки серые)
Открыть Wgplex…
Выход
```

- Галочка — туннель включён, щелчок переключает. ⚠ — включён, но мёртв или не поднялся.
- Строка проблемы (правило на резерве или в fallback, ошибка конфига, демон недоступен) открывает окно на нужном месте.
- Без права управления (`can_control: false`) туннели и «Приостановить» неактивны.
- Иконка — template: контурный щит (всё выключено), залитый (работает), с «!» (проблема), с паузой.

### 17.4. Окно

Боковая панель и содержимое раздела (SwiftUI). Приложение без значка в Dock (`LSUIElement`); значок появляется, пока окно открыто.

- **Панель действий** во всех разделах: Приостановить/Возобновить, Выключить все, Перечитать конфиг. Без права управления — неактивны.
- **Баннер** сверху: ошибка конфига, демон недоступен, пауза, правило на резерве, доступна новая версия.
- **Туннели:** список с переключателями; детали выбранного — endpoint, интерфейс и адрес, handshake, трафик, маршрутов, проверка.
- **Правила:** сервисы, `via`, текущий туннель, состояние.
- **Диагностика:** поле `explain`, таблица маршрутов.
- **Логи:** хвост файла из `log_path`, поиск, фильтр по уровню, дочитывание, пока раздел открыт.
- **Открыть папку конфига** — если `config_dir` доступен текущему пользователю на чтение (на практике владелец); иначе — путь и «Конфиг правит администратор».
- **Настройки** (⌘,): запуск при входе, уведомления, путь к сокету, проверка обновлений.

### 17.5. Автозапуск

- `SMAppService.mainApp` (видно в «Объектах входа» → «Open at Login» одной записью под своим именем). С ad-hoc подписью регистрация — сразу `enabled`, без одобрения; система один раз показывает уведомление. Регистрация переживает обновление бандла с другим cdhash и перезагрузку — запись та же (M0, S1–S5). После `unregister` запись остаётся выключенной, повторная регистрация уведомления не даёт (S6).
- По умолчанию выключен. При первом запуске — один вопрос «Запускать Wgplex при входе?» и запрос разрешения на уведомления.
- Каждый пользователь включает сам. Для всех пользователей сразу — команда для админа в README (plist в `/Library/LaunchAgents`), без привилегированного кода в приложении.

### 17.6. Уведомления

Приложение сравнивает соседние ответы `status.get` (раз в 10 с); движок не меняется. Работают, пока приложение запущено.

| Событие | Пример |
|---|---|
| Туннель включён, но умер или не поднялся, и правила ушли на резерв или в fallback | «nl не отвечает: youtube, ai → de» |
| Восстановление | «nl снова работает, youtube через nl» |
| Ошибка конфига при `reload` | «Изменения конфига не применены: 2 ошибки. Работает прежний конфиг» |
| Ошибка конфига при старте | «wgplex запущен без туннелей: конфиг с ошибками» |
| Демон пропал / вернулся | «wgplex не работает» |
| Новая версия приложения (17.1) | «Доступна Wgplex 1.3» — один раз на версию |

- Не уведомляет о намеренных действиях (пауза, переключения) и о результате собственного «Перечитать» — он виден в окне.
- События одного опроса — одно уведомление; о «мигающем» туннеле — не чаще раза в 5 минут.
- Одна галочка в настройках, по умолчанию включена. Щелчок открывает окно на нужном разделе.

### 17.7. Сборка

Swift Package, macOS 13+, без сторонних зависимостей. `make dmg` — `swift build -c release --arch arm64 --arch x86_64`, бандл, ad-hoc подпись с постоянным требованием `codesign --sign - -r='designated => identifier "io.github.mrfokin.wgplex"'` (иначе требование — cdhash, и при `brew upgrade --cask` Homebrew пишет «signer changed» и не переносит одобрение, M0, K8, K9), `hdiutil create`; релиз — `gh release create` с `.dmg` (16.1). Код — копия `app/` Wirefork (клиент RPC, модели статуса) без чтения и отправки конфига; меню переписывается на AppKit. Логика (клиент, представление статуса, вычисление уведомлений) — в библиотечном таргете под XCTest, с фейковым сервером API.

## 18. Ограничения v1

- Не больше 1000 зон захвата DNS (8). Зона чужого VPN, более длинная, чем наша (`www.example.com` при нашей `example.com`), забирает свои имена.
- Ограничения DNS Wirefork (16): DoH в браузере, iCloud Private Relay, scoped-запросы, `/etc/resolver/*`, CNAME на сторонний CDN.
- Туннели и правила общие: трафик всех пользователей машины идёт по конфигу владельца.
- Root запускает бинарник из каталога владельца prefix (5).
- Уведомления — только пока у пользователя запущено приложение.
- Wirefork и wgplex на одной машине друг другу маршрутов не удаляют (свои метки, 4.1), но их правила на одних префиксах конфликтуют, а захват DNS у каждого свой: одновременная работа не поддерживается.
- Без Developer ID приложение разрешается вручную при установке и при каждой ручной замене из `.dmg`; `brew upgrade --cask` — без этого.
- Остальные ограничения маршрутизации — как в Wirefork 16.

## 19. Вне v1

- Редактор конфига в окне (для владельца): структурная правка через CLI на Go (`wgplex config …` поверх `yaml.v3` `Node`, с сохранением комментариев), проверка — `wgplex check -json`.
- Пункт «Запускать для всех пользователей» в приложении.
- Хуки на события (скрипт при уходе правила на резерв).
- CI: `make check` на push, релиз и обновление формулы по тегу.
- Developer ID, подпись и нотаризация приложения.
- Режим «весь трафик через туннель X» (как в Wirefork 17).

## 20. Spike перед разработкой

Этап M0, в VM tart через `scripts/vm.sh` (CLAUDE.md, «Root и система»). Подготовка:

- образ `wgp-base`: Homebrew, гостевой агент tart (общий буфер обмена с хостом), вход по SSH только по ключу, `sudo` для `admin`;
- bridged-сеть поверх Wi‑Fi хоста; если не работает — NAT и DNS VM на публичный резолвер;
- WireGuard-сервер во второй VM — тестовый стенд для этапа здоровья и failover, не для M0.

Проверки:

1. **Точечный захват DNS:** `SupplementalMatchDomains` со списком зон (сотни доменов), приоритет перед `[""]` чужого VPN, `ServerPort` с нестандартным портом.
2. **`dsmemberutil checkmembership`:** вложенные группы, время вызова, поведение для несуществующих uid и группы.
3. **`SMAppService.mainApp` с ad-hoc подписью:** регистрация, обновление на новую сборку, перелогин.
4. **Неподписанный cask на Homebrew 7** из стороннего tap: ставится ли, что при `brew upgrade --cask`.
5. **Формула со службой от root:** `service do … require_root true`, `sudo brew services start`, затем `upgrade`, `uninstall`, `cleanup` от пользователя — владельцы путей, перезапуск службы, stderr до `dup2`.

Факты — `docs/plans/m0-spike.md`, «Факты spike».
