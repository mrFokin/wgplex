# wgplex — документ проектирования (черновик)

Статус: черновик, 2026-10-20. Собран по обсуждению, уточнён по фактам spike M0 и ревью дизайна; на M1 в него перенесён текст разделов Wirefork (4.4).

wgplex — отдельный продукт на основе кода Wirefork. Ядро (туннели, маршрутизация, DNS, здоровье) переносится копией и дальше развивается независимо. Текст разделов `wirefork/docs/design.md` (`master` на `c86f993`, v1.2.0) перенесён сюда на M1 с заменами из 4.4; дальше документ самостоятельный.

## 1. Задача

Несколько WireGuard-туннелей одновременно на macOS с раскладкой трафика по правилам — как Wirefork, но в другой модели владения:

| | Wirefork | wgplex |
|---|---|---|
| Машины | Mac с несколькими пользователями, у каждого свои туннели | Mac одного человека или общий набор туннелей на машину |
| Чьи туннели | пользователя за консолью | машины |
| Когда поднимаются | при входе пользователя | при загрузке |
| Выход и смена пользователя | сброс | ничего не меняется |
| Конфиг | у каждого пользователя, присылает приложение | один на машину, демон читает сам |
| Установка | `.pkg` | Homebrew |

Опорный сценарий:

- туннели: домашний, рабочий, два зарубежных (nl, de);
- рабочие адреса (перечислены в `AllowedIPs` рабочего конфига) — через рабочий туннель, рабочие домены резолвятся через рабочий DNS;
- YouTube, AI-сервисы и т.п. — через зарубежный туннель с приоритетом (nl, при недоступности — de); список сервисов меняется;
- домашний туннель обычно выключен, включается вручную вне дома;
- пересечения адресов решаются порядком туннелей;
- всё остальное — напрямую;
- админ ставит и настраивает wgplex через brew, работает в CLI;
- остальные пользователи машины видят статус и, если им разрешено, переключают туннели из меню `Wgplex.app`.

## 2. Рамки

**Платформа:** macOS 13 Ventura и новее, Apple Silicon и Intel. Linux не поддерживается: системный слой (utun, `PF_ROUTE`, SCDynamicStore) — только darwin.

**Аудитория:** публичный open-source проект. Админы — CLI через brew; пользователи «попроще» — приложение.

**Состав:**

- `wgplex` — движок: демон и CLI в одном бинарнике, репозиторий `mrFokin/wgplex`, формула `wgplex` в tap `mrFokin/homebrew-tap`;
- `Wgplex.app` — меню в строке состояния и окно, репозиторий `mrFokin/wgplex-app`, `.dmg` в релизах и cask `wgplex-app` (раздел 17).

Движок ничего не знает о приложении: приложение — один из клиентов публичного API (раздел 14).

**Не входит в v1** — раздел 19.

## 3. Имена и пути

`<prefix>` — `HOMEBREW_PREFIX`; все пути по умолчанию выводятся из него, флаги нужны только для отладки. Бинарник готовый и universal (16), поэтому prefix определяется при запуске:

1. путь к исполняемому файлу без симлинков содержит `/Cellar/` — prefix — всё до `/Cellar/` (установка через brew, в том числе в нестандартный prefix);
2. иначе — по архитектуре процесса: `/opt/homebrew` на arm64, `/usr/local` на x86_64 (сборка для разработки, `make build`).

| Что | Значение |
|---|---|
| Продукт | wgplex |
| Go-модуль | `github.com/mrFokin/wgplex` |
| Бинарник | `<prefix>/bin/wgplex` |
| Конфиг | `<prefix>/etc/wgplex/wgplex.yaml` + `*.conf` рядом (симлинки допускаются) |
| Сокет | `<prefix>/var/run/wgplex.sock` |
| Состояние | `<prefix>/var/wgplex/state.json` |
| Лог | `<prefix>/var/log/wgplex/wgplex.log` (+ архивы, раздел 15) |
| Сервис | `sudo brew services start --sudo-service-user=root wgplex` (LaunchDaemon `sh.brew.wgplex`, plist `/Library/LaunchDaemons/sh.brew.wgplex.plist` генерирует brew, 16.4) |
| Приложение | `/Applications/Wgplex.app`, bundle id `io.github.mrfokin.wgplex` |

### 4.1. Демон

- `wgplex daemon` запускается launchd при загрузке, работает от root, перезапускается при падении (`KeepAlive`, кроме выхода с кодом 0).
- Запущен не от root (`brew services start` без `sudo` ставит копию как LaunchAgent пользователя, M0, H7) — ошибка в stderr (лог root ему недоступен) и выход с кодом 0: launchd его не перезапускает (16.4; проверка — M6).
- Каталоги `var/wgplex`, `var/log/wgplex` и `var/run` (для сокета) создаёт формула (10.3); демон создаёт только недостающее внутри `var/wgplex` и `var/log/wgplex`. Родителей (`var`, `var/log`, `var/run`) не создаёт: созданный root общий каталог ломает brew пользователю (M0, H6); нет каталога — ошибка в stderr.
- Со старта читает конфиг и поднимает туннели по состоянию (11) — вход пользователя не нужен (при FileVault — после разблокировки диска, 18).
- Не следит за пользователем за консолью: ни сброса при выходе, ни переключателей на пользователя.
- Конфиг с ошибками при старте — демон работает без туннелей, но со снимком блокировки (9.1), ошибка в `status.get`; не падает (иначе `KeepAlive` гонял бы перезапуски).
- При старте маршруты и ключ захвата DNS, оставшиеся от прошлого запуска, не снимаются заранее: демон сразу синхронизирует таблицу и ключ с новым состоянием, лишнее уходит при синхронизации. Так `fallback: block` не прерывается при перезапуске после падения (9.1).
- SIGHUP и SIGUSR1 игнорируются явно (`signal.Ignore`): по умолчанию они завершили бы процесс без уборки.
- Второй экземпляр (например, `sudo ./build/wgplex daemon` при работающей службе — пути те же) завершается с ошибкой на захвате сокета (14).
- Свои метки, отличные от Wirefork: маршруты помечаются `RTF_PROTO2` (у Wirefork — `RTF_PROTO1`; `RTF_PROTO3` занят ядром, `RTPRF_OURS` в `net/route.h`), у синтетического DNS-сервиса (8) — свой постоянный UUID. Демон удаляет и заменяет только маршруты со своим флагом, поэтому маршруты Wirefork или другой копии кода для него чужие (7.2: не трогаются, предупреждение в лог). Отдельной проверки на Wirefork нет.

## 5. Модель угроз и доступ

**Владелец prefix brew — доверенный, фактически равен root:** ему принадлежит бинарник, который root запускает как демон (с `--sudo-service-user=root` владелец бинарника не меняется, 16.4). Защищаться от него бессмысленно. Homebrew делает каталоги prefix записываемыми для группы `admin`, а у её членов и так есть `sudo` — они тоже доверенные. Защищаемся только от **остальных** пользователей машины.

Следствия:

- демон (root) читает файлы из каталога конфига; симлинки допускаются;
- **владелец каталога конфига** — по `stat` каталога при каждой проверке прав; каталога нет — управляет только root;
- каталог конфига и каждый читаемый файл (после разрешения симлинка) принадлежат root или владельцу каталога и не записываемы для группы и остальных — иначе ошибка конфига: посторонний мог бы перенаправить трафик. Предки каталога сознательно не проверяются (группа `admin` доверенная);
- читаются только обычные файлы (FIFO или устройство на месте `.conf` подвесили бы демон при старте), не больше 1 МБ каждый; только `wgplex.yaml` и `.conf`, на которые ссылаются туннели (в Wirefork клиент отправлял все `*.conf` каталога);
- `.conf`, доступный на чтение группе или остальным, — предупреждение (как у `wg-quick`);
- **TCC:** демону, запущенному launchd, без Full Disk Access недоступны `~/Documents`, `~/Desktop`, `~/Downloads`, iCloud Drive и съёмные тома. Симлинк на `.conf` там — ошибка чтения; при `EPERM` текст ошибки называет TCC и советует перенести файл в каталог конфига. `wgplex check` из Terminal работает с правами TCC Terminal и такой файл прочитает — расхождение записано в 18;
- сокет `0666`, права — по методам:

| Методы | Кто |
|---|---|
| `status.get`, `diag.*` | все |
| изменяющие (`config.reload`, `tunnel.*`, `daemon.*`) | root, владелец каталога конфига, члены `control_group` |

- uid соединения — `LOCAL_PEERCRED`. Группы из `LOCAL_PEERCRED` не используются: их не больше 16, а у администратора macOS их часто больше. Членство проверяется через Directory Services вызовом `mbr_check_membership` (cgo, `membership.h`; uid и имя группы → UUID через `mbr_uid_to_uuid` и `mbr_identifier_to_uuid`). Учитывает вложенные группы, изменения членства видны сразу, 0,1–2 мс, root не нужен (M0, G1, G5, G7). `dsmemberutil` не используется: код выхода у «член» и «не член» одинаковый (M0, G2).
- Членство проверяется в изменяющих методах и в `status.get` (поле `can_control` и урезание ответа, ниже) — с кэшем по uid на 30 с (константа): `status.get` опрашивается каждые 1–10 с у каждого пользователя.
- `control_group` — имя группы в `wgplex.yaml`, по умолчанию `admin`. Несуществующая группа (`ENOENT` при поиске имени; у числового gid она неотличима от «не член») — ошибка конфига; пока конфиг не применён, управляют только root и владелец.
- Ключи не попадают в логи и ответы API (10.1, «Ключи»).

**Видимость.** Тот, кто может управлять (`can_control`), видит всё. Остальным `status.get` и `diag.*` отдают урезанный ответ: имена и состояния туннелей, сервисы и `via` правил, текущий туннель и причина fallback — есть; нет endpoint'ов и адресов пиров, адреса или URL `check` (в URL может быть токен), `names` в маршрутах (имена, которые резолвили другие пользователи), текста ошибок конфига (вместо него — их число). Лог — `0640`, группа `control_group` (15).

## 6. Туннели

- Каждый туннель — отдельный `device.Device` поверх `tun.CreateTUN("utun", mtu)`, настройка через UAPI (`IpcSet`).
- Адреса (`Address`) и MTU из `.conf` назначаются интерфейсу. Без `MTU` — 1420 (как у `wg`). Маршрут на подсеть `Address` не ставится (как у `wg-quick`).
- Endpoint-домен резолвится при подъёме туннеля: первый IPv4-адрес, при его отсутствии — первый IPv6. Резолв идёт мимо собственного резолвера демона (8); текст ошибки называет серверы, на которые ушёл запрос.
- Для каждого endpoint ставится host-route через текущий физический шлюз, чтобы UDP туннеля не уходил в другие туннели. Ставится до назначения адресов интерфейсу: wireguard-go поднимает устройство, как только интерфейс получает `IFF_UP`. Если физического шлюза нет (нет сети, основной маршрут ведёт в utun или другой VPN), на endpoint ставится blackhole-маршрут и туннель поднимается — ни утечки, ни петли. Пересоздаётся при смене сети.
  - Интерфейсы `utun*`, `ipsec*` (IKEv2) и `ppp*` (L2TP, PPPoE) — туннели, а не физические; `lo*` — тоже не физический.
  - Endpoint в локальной сети (прямой маршрут на подсеть или host-запись через физический интерфейс, в том числе равный адресу шлюза) host-route не получает: он уже идёт напрямую. Основной маршрут и его половинки (`0/1`, `128/1`) локальной сетью не считаются.
  - Если на endpoint уже стоит чужой (без флага `RTF_PROTO2`) host-route, туннель не поднимается с ошибкой; чужой маршрут не трогается.
- Все маршруты wgplex помечаются флагом `RTF_PROTO2` (4.1); демон удаляет и заменяет только помеченные маршруты. Помеченные маршруты, оставшиеся от прошлого запуска, при старте заранее не снимаются — лишнее уходит при синхронизации (4.1); utun и его адреса исчезают сами.
- Сменой сети считается изменение шлюзов, системных DNS или первичного сервиса (`PrimaryService` в `State:/Network/Global/IPv4`). Изменения ключей других сервисов (чужой VPN, IPv6-адреса) при прежних значениях сменой сети не считаются. Пробуждение обрабатывается всегда.
- При смене сети (SCDynamicStore) и после пробуждения:
  - заново берутся системные DNS и шлюзы;
  - host-route'ы до endpoint'ов переносятся на новый шлюз; неудавшиеся повторяются;
  - сокеты туннелей переоткрываются (`BindUpdate`), начинается повторный handshake; после пробуждения текущие ключи WireGuard сбрасываются, потому что сервер их уже выбросил;
  - окно проверки здоровья сбрасывается (9), отсчёт возврата на приоритетный туннель — тоже (9.2);
  - туннели, которые не поднялись, поднимаются заново;
  - правила пересчитываются (7.3);
  - проверяется захват DNS (8).

  Перед сном ничего не делается.
- События читаются долгоживущим `scutil` (`n.watch`) без cgo, с перезапуском при выходе. Пробуждение — скачок настенного времени относительно монотонного больше 5 с. Раз в 30 с — сверка на случай потерянных уведомлений. События сливаются: 500 мс тишины, не дольше 3 с.
- **Перерезолв hostname endpoint'а (DDNS).** Endpoint'ы с hostname резолвятся заново у работающих туннелей при смене сети и пробуждении, у мёртвого туннеля (9) — не чаще раза в 60 с. Если адрес пира изменился: ставится host-route до нового адреса, endpoint пира меняется через UAPI (`update_only`) без перезапуска туннеля, host-route до старого адреса снимается, начинается повторный handshake. Ошибка резолва или маршрута — предупреждение в лог, остаётся старый адрес.
- **Повтор подъёма.** Туннель, который не поднялся (`error`), поднимается заново при смене сети и раз в 60 с после неудачи; без сети (нет физического шлюза, 9) — нет, в том числе при смене сети, которая сеть убрала.
- Поля `.conf`, специфичные для `wg-quick` (`PreUp`, `PostUp`, `Table`, `SaveConfig` и т.п.), игнорируются с предупреждением в логе.
- В `.conf` может быть несколько `[Peer]`.
- Не-IP значения в `DNS` (поисковые домены `wg-quick`) игнорируются с предупреждением — для этого есть `dns_domains`.
- Длина строки `.conf` не ограничена: рабочие конфиги содержат сотни адресов в одной строке `AllowedIPs`.

### 6.1. Режим маршрутов

`AllowedIPs` в `.conf` — это одновременно криптофильтр WireGuard и (в `wg-quick`) список маршрутов. wgplex разделяет эти роли через поле `routes`:

- `config` — `AllowedIPs` попадают в таблицу маршрутов (рабочий, домашний);
- `rules` — в таблицу попадают только адреса из правил; `AllowedIPs` остаются только криптофильтром (зарубежные с `0.0.0.0/0`).

## 7. Маршрутизация

### 7.1. Источники маршрутов

1. Host-routes до endpoint'ов через физический шлюз — всегда.
2. `AllowedIPs` туннелей в режиме `config`.
3. CIDR из сервисов в правилах.
4. Динамические `/32` (и `/128`, если туннель поддерживает IPv6) из DNS-ответов по доменам из правил. Для правил без туннеля (пустой `via` — `direct`, `fallback: block` — `reject`) `/128` ставится всегда.
5. Всё остальное — основной маршрут системы (напрямую).

### 7.2. Разрешение пересечений

- Побеждает более узкий префикс (обычный longest-prefix match).
- При одинаковых префиксах от разных источников: host-route до endpoint'а > правила > `AllowedIPs`. Между правилами решает порядок правил, между `AllowedIPs` разных туннелей — порядок туннелей в конфиге (выше — приоритетнее).
- Следствие: динамические `/32` из правил по доменам перекрывают подсети и совпадающие адреса из `AllowedIPs`.
- Один адрес из DNS-ответов по доменам нескольких правил (общий CDN) обслуживается правилом, стоящим выше.
- `AllowedIPs` туннеля в режиме `config` и host-route до его endpoint'а остаются в таблице, пока туннель включён, даже если он мёртв (утечка мимо туннеля хуже недоступности). Снимаются при выключении.
- IPv6-префикс с целью «туннель» (CIDR сервиса, `AllowedIPs`) у туннеля без IPv6-адреса в `Address` становится `reject`: ядро не принимает IPv6-маршрут на интерфейс без IPv6-адреса, а напрямую такой трафик уйти не должен. Приложения сразу получают ошибку и переходят на IPv4.

Демон рассчитывает итоговую таблицу в памяти и синхронизирует её с таблицей ядра (`PF_ROUTE`), добавляя/удаляя только разницу:

- текущее состояние — наши маршруты (`RTF_PROTO2`) из дампа таблицы ядра при каждой синхронизации, в памяти не хранится;
- «туннель» — маршрут на utun туннеля; пока у включённого туннеля нет utun (пересоздаётся, не поднялся), его маршруты — `reject`, чтобы трафик не ушёл напрямую; «напрямую» — через текущий физический шлюз своего семейства (6), без шлюза маршрут не ставится (предупреждение в лог), он появится при следующей синхронизации после появления сети; `reject` — `RTF_REJECT` на `lo0`, приложение сразу получает ошибку;
- смена туннеля или шлюза у сети — без удаления маршрута (`RTM_CHANGE` с маской); у host-маршрута (`/32`, `/128`) и при смене вида цели — удаление и добавление подряд (`RTM_CHANGE` без маски ищет охватывающий маршрут и может изменить чужой);
- чужой маршрут на тот же префикс (подсеть локальной сети, ручной `route add`, другой VPN) не трогается: наш не ставится, предупреждение в лог, остальная таблица применяется;
- host-route'ы до endpoint'ов ставятся и снимаются вместе с туннелем (6), синхронизация их не трогает;
- scoped host-route'ы (`RTF_IFSCOPE`) до DNS-серверов туннеля (8) ставятся после подъёма туннеля и исчезают вместе с его utun; синхронизация их не трогает.

### 7.3. Правила

```yaml
rules:
  - services: [youtube]
    via: [nl, de]
    fallback: default
```

- `via` — упорядоченный список туннелей; используется первый **включённый переключателем (11) и живой** (9).
- Пустой `via` — всегда напрямую (исключение): для CIDR и адресов правила ставятся явные маршруты через физический шлюз, перекрывающие, например, подсети из `AllowedIPs`.
- `fallback`, если ни один туннель из `via` не работает:
  - `default` — основной маршрут (сейчас — напрямую): маршрутов правила в таблице нет, решает остальная таблица;
  - `block` — трафик блокируется: DNS для доменов правила отвечает пустым ответом (NODATA), для CIDR и уже известных IP ставятся `reject`-маршруты (`RTF_REJECT`: соединение сразу завершается ошибкой, а не висит до таймаута). Это гарантия (9.1).
- Правило, ушедшее на резерв, возвращается на более приоритетный туннель по 9.2. При переключении открытые соединения рвутся. После применения конфига выбор делается заново.
- Правила используют только туннели, включённые переключателем (11); выключенный туннель для правил не существует и автоматически не поднимается. На паузе туннели опущены, правила — в fallback (12).

### 7.4. Сопоставление доменов

- `youtube.com` — суффикс: сам домен и все поддомены.
- `=google.com` — точное совпадение.
- Побеждает самое точное совпадение (точное > более длинный суффикс > короткий суффикс), при равенстве — порядок правил.
- Решение принимается по запрошенному имени; CNAME-цепочка не анализируется.
- Правило в `fallback: default` в сопоставлении доменов не участвует: имя достаётся следующему подходящему правилу по тем же правилам точности (8).
- Имя из запроса сравнивается без учёта регистра, точка в конце игнорируется (`WWW.YouTube.com.` совпадает с `youtube.com`).
- Масок, ключевых слов и регулярных выражений нет.

## 8. DNS

- Демон поднимает резолвер на `127.0.0.1` (только loopback; порт — ниже, «Адрес резолвера»), и система направляет в него имена из зон (ниже, «Точечный захват»). Настройки сетевых сервисов не меняются, поэтому сохранять нечего.
- **Выбор апстрима** по запрошенному имени, по порядку:
  1. правило по 7.4; правило в `fallback: default` в сопоставлении не участвует, имя достаётся следующему подходящему правилу (как CIDR в 7.3);
  2. правило в `fallback: block` — NODATA на любой тип запроса, апстрим не спрашивается;
  3. правило на туннеле — запрос через этот туннель;
  4. правило с пустым `via` — исходные DNS системы;
  5. `dns_domains` туннелей, у которых есть utun: самая длинная зона, при равенстве — порядок туннелей;
  6. остальное — исходные DNS системы.
- **Домены из правил:** запрос уходит через целевой туннель. Сокет привязан к интерфейсу через `IP_BOUND_IF`, поэтому одинаковые DNS-серверы у разных туннелей не конфликтуют. Одной привязки ядру мало, поэтому до каждого DNS-сервера туннеля ставится scoped host-route (`RTF_IFSCOPE`) на его utun. Он не мешает обычным маршрутам до того же адреса.
  - До ответа приложению демон ставит `/32` (`/128`) через этот туннель. Если маршрут поставить не удалось, приложение получает SERVFAIL: ответ без маршрута отправил бы соединение напрямую. SERVFAIL отдаётся, только если не встал маршрут адреса этого ответа: ошибка записи другого префикса ответ не блокирует.
  - Маршрут живёт по паре «имя — адрес»: срок равен TTL + 1 ч и продлевается каждым ответом. Адрес, общий для нескольких имён, живёт до самого позднего срока. Запас большой, потому что снятый маршрут рвёт открытые TCP-соединения, а QUIC пустил бы напрямую. Пар не больше 4096, при переполнении вытесняется самая ранняя.
  - Правило для адреса определяется по имени заново при каждом пересчёте таблицы. Поэтому при смене fallback, выключении туннеля и `config.reload` адреса сами переезжают между правилами.
  - DNS-сервер для туннеля — `DNS` из его `.conf`; если не задан — `1.1.1.1` через туннель. Отдельного поля в YAML нет.
  - Другие типы записей (MX, TXT и т.п.) уходят тем же апстримом. У HTTPS/SVCB удаляются `ipv4hint` и `ipv6hint`, иначе клиент может подключиться по ним мимо `/32`.
- **`dns_domains` туннеля:** запросы уходят через туннель на DNS из его `.conf` (split DNS), без динамических маршрутов. Если у туннеля нет utun (выключен или не поднялся), запросы идут на исходные DNS системы, как будто поля нет.
- **Остальное:** исходные DNS-серверы системы — DNS первичного сервиса (ручные, иначе из DHCP), обновляются при смене сети. PTR вне зон в резолвер не приходит; обратные зоны рабочих сетей можно добавить в `dns_domains`.
- Собственные запросы демона (endpoint'ы, 6) идут напрямую на исходные DNS системы, мимо системного резолвера и потому мимо резолвера демона.
- Своего кэша нет, кэширует mDNSResponder. Одновременно — не больше 256 запросов к апстримам, таймаут — 2 с на сервер; сервер не ответил или ответил SERVFAIL/REFUSED — запрос идёт следующему; если лучшего ответа нет, клиент получает последний такой ответ, а если не ответил ни один — SERVFAIL.
- **IPv6:** при `ipv6_filter: true` (по умолчанию) для доменов из правил AAAA-ответы отбрасываются, если целевой туннель не поддерживает IPv6.

**Точечный захват.** Синтетический сервис `State:/Network/Service/<постоянный UUID wgplex>/DNS` (свой, не Wirefork, 4.1) публикует не `SupplementalMatchDomains = [""]` (все имена), а только нужные зоны:

- домены сервисов из всех правил (`=example.com` — зона `example.com`);
- `dns_domains` туннелей.

Ключ сервиса (M0, D1–D7, D11):

| Поле | Значение |
|---|---|
| `ServerAddresses` | `[127.0.0.1]` |
| `ServerPort` | порт резолвера (ниже) |
| `SupplementalMatchDomains` | зоны |
| `SupplementalMatchOrders` | для каждой зоны — `1`: при той же зоне у чужого VPN выигрывает wgplex (без явного порядка победитель случаен, D7). Что меньшее значение выигрывает, spike не проверил — проверка M4 |
| `SupplementalMatchDomainsNoSearch` | `1`: иначе все зоны попадают в search list, короткие имена и каждый сброс кэша дают сотни запросов |

- Других ключей (`Setup:`, `State:/Network/Global/DNS`) не нужно.
- Запись — через SystemConfiguration (`SCDynamicStoreSetValue`, cgo), не `scutil`: `scutil` принимает не больше 99 значений поля и молча обрезает длинные строки (M0, D2). Запись 500 зон — 10–15 мс, ответы по новым зонам — через ~0,1 с.
- После записи и снятия ключа сбрасывается кэш mDNSResponder. Перезагрузка убирает ключ сама; перезапуск configd — тоже: демон проверяет ключ при его изменении, при событиях сети и раз в 30 с и ставит заново (18).
- **Лимит — 1000 зон**, больше — ошибка конфига. Около 4000 зон система молча оставляет прежнюю DNS-конфигурацию (предел зависит от длины имён, M0, D9). После записи демон проверяет разбором `scutil --dns`, что резолверы для зон появились (приватный `dns_configuration_copy` не используется: недокументированный ABI, `dnsinfo.h` под APSL); нет — ошибка в `status.get` и лог.
- Конкретная зона выигрывает у `[""]` чужого VPN при любом порядке публикации: решает самый длинный суффикс (M0, D5). Более длинная зона чужого сервиса (`www.example.com` против нашей `example.com`) забирает свои имена — ограничение (18).
- Резолвер отвечает на любые типы запросов, в том числе `SVCB _dns.resolver.arpa` (DDR от mDNSResponder, M0, D12).

Остальные имена mDNSResponder резолвит сам, мимо демона. Следствия:

- сбой или перезапуск демона ломает только имена из правил, а не весь DNS машины: они не резолвятся около 60 с (к исходному DNS сами не уходят, M0, D10), остальные работают. Поэтому при остановке демон снимает ключ первым делом — это сразу освобождает и зависшие запросы. Ключ постоянный, не `SCDynamicStoreAddTemporaryValue`: при падении демона имена из правил лучше минуту не резолвить, чем пустить мимо туннеля;
- конкретный supplemental-домен точнее `[""]` чужого VPN — имена из правил работают и рядом с ним (в Wirefork они шли мимо);
- в резолвер приходят и поддомены зон, которым правило не подходит (`mail.google.com` при `=google.com`), и имена правил в `fallback: default` — они уходят исходным DNS системы (выбор апстрима выше; при чужом VPN с `[""]` — мимо его DNS, 18);
- **зоны — функция только конфига:** захват есть, если список зон не пуст, меняется при `config.reload`; пауза, «Выключить все», состояние туннелей и резолвера его не меняют (12, 9.1): правила в `block` продолжают блокировать, правила с пустым `via` — работать.

**Адрес резолвера** — `127.0.0.1` на нестандартном порту (ключ `ServerPort`), порт — константа. `127.0.0.1:53` часто занят: dnsmasq (в том числе Laravel Valet для `*.test`), sing-box, dnscrypt-proxy, unbound, AdGuard Home. На своём порту wgplex работает рядом с ними: благодаря точечному захвату имена из правил идут в wgplex, остальные — тому, кто на `:53`. `ServerPort` у supplemental-резолвера работает (M0, D3); вид `127.0.0.1.<порт>` в `ServerAddresses` — нет (D11).

**Порт занят — fail-closed.** Демон не падает (иначе `KeepAlive` гонял бы перезапуски). Зоны публикуются всё равно: на порту никто не отвечает, и имена из правил **не резолвятся**, а не уходят исходному DNS (M0, D10) — для `block` это гарантия (9.1), для правил с `via` — недоступность вместо утечки (7.2). CIDR-правила работают. Ошибка — в `status.get` (`icon: warn`) и в лог; повтор — раз в 60 с и при `config.reload`. Цена: пока порт занят, не резолвятся и поддомены зон, которым ни одно правило не подходит.

## 9. Здоровье и failover

- **Пассивная проверка:** туннель считается мёртвым, если последний handshake старше ~3 минут при исходящем трафике.
- **Активная проверка:** если задан `check`, ping на этот адрес (IP) или HTTP-запрос по URL через интерфейс туннеля. Интервал 10 с, мёртв после 3 неудач подряд, жив после 1 успеха. Параметры — константы, в конфиг не выносятся.
- Мёртвый туннель исключается из `via` всех правил; правила переезжают на следующий туннель.

Уточнения:

- **Начало.** Состояние после подъёма туннеля — «неизвестно». Для маршрутизации оно считается живым.
- **Пассивная проверка — точнее.** Туннель мёртв, если на двух опросах подряд tx вырос, а rx не вырос, и handshake старше 180 с. Одного опроса мало: при выходе из простоя он может попасть между попыткой handshake и ответом на неё. Отсчёт идёт от handshake, но не раньше подъёма туннеля или сброса. Опросы — раз в 10 с.
  - Жив — при росте rx или если handshake не старше 180 с.
  - Без трафика вердикт не меняется.
- **Итоговый вердикт.** Туннель мёртв, если мёртв хотя бы один вердикт — активный или пассивный. Жив после успеха ping, свежего handshake или роста rx.
- **Сброс.** Смена сети и пробуждение сбрасывают окно и счётчик неудач. Мёртвый туннель остаётся мёртвым до свидетельства жизни.
- **Без сети** (нет физического шлюза ни IPv4, ни IPv6) опросы не делаются и вердикты не меняются. Без сети недоступны все туннели, и failover только перетасовал бы правила. При возврате сети окно сбрасывается (6).
- **Повторный handshake.** Мёртвому туннелю — раз в 30 с: без трафика он иначе не оживёт.
- **Ожившие туннели.** Правило, ушедшее на резерв, возвращается на оживший туннель по 9.2. Правило в fallback его подхватывает.
- **Ping.**
  - Свой ICMP-сокет на туннель, привязанный к utun (`IP_BOUND_IF`), и scoped host-route до `check`, как для DNS-серверов (8). Поэтому ping идёт через свой туннель, даже когда правила ушли на другой.
  - Таймаут ping — 3 с.
  - `check` другого семейства, чем `Address` туннеля, не пингуется: предупреждение конфига (10.2), работает только пассивная проверка.
  - Туннелю, который ICMP не пропускает, нужна HTTP-проверка: ping на нём всегда неудачен.
- **HTTP.**
  - `check: http://…` или `https://…` — `GET` по URL через utun: сокет с `IP_BOUND_IF` и scoped host-route до адреса, как у ping. Без редиректов, без keep-alive (каждая проверка — новое соединение), без системного прокси, сертификат проверяется по имени из URL.
  - Успех — любой HTTP-ответ, статус не важен: проверяется путь через туннель, а не сервер. RTT — до заголовков ответа, включая резолв, TCP и TLS (с ping не сравним). Таймаут — 5 с.
  - Имя хоста резолвится на каждой проверке через DNS туннеля (8) сокетом, привязанным к utun; семейство — IPv4, если в `Address` есть IPv4, иначе IPv6. Ошибка резолва — неудача.
  - IP-литерал в URL другого семейства, чем `Address`, не проверяется: предупреждение конфига (10.2). Так же — имя хоста, когда у туннеля нет DNS-сервера (8), достижимого через него: семейства, которое есть в `Address` (например, только IPv6 в `Address` и DNS по умолчанию `1.1.1.1`). Работает только пассивная проверка.
  - Резолвер — Go-резолвер с серверами туннеля; `/etc/hosts` учитывается, как и при резолве endpoint'ов (6).
  - Неудачи и вердикт — как у ping. В причине — последняя ошибка (`http <url>: 3 failures (…)`).
- Мёртвый туннель сохраняет utun. Его `AllowedIPs` в режиме `config` остаются на нём (7.2).

### 9.1. Гарантия `fallback: block`

`block` — гарантия, пока служба включена: трафик сервисов правила не уходит напрямую ни в каком состоянии демона.

| Состояние | Как держится |
|---|---|
| Туннели `via` мертвы или выключены, пауза, «Выключить все» | fallback правила — reject-маршруты и NODATA (7.3, 8) |
| Битый конфиг при старте | **снимок блокировки**: CIDR и домены правил `block` из последнего удачно применённого конфига (без ключей), поле `block` в `state.json` (11). Демон ставит reject-маршруты на CIDR, публикует зоны доменов и отвечает на них NODATA. Туннелей нет |
| Порт резолвера занят | fail-closed: зоны опубликованы, имена не резолвятся (8) |
| Падение демона | reject-маршруты и ключ захвата остаются (ключ постоянный, 8); через ~60 с имена из зон перестают резолвиться (M0, D10), а не уходят мимо. После перезапуска — синхронизация без предварительной уборки (4.1) |
| Остановка службы, удаление | вне гарантии: намеренное действие root; демон снимает маршруты и ключ |
| Секунды при загрузке до старта демона | вне гарантии (18) |

Снимок обновляется при каждом удачном применении конфига. Пустой конфиг или конфиг без правил `block` даёт пустой снимок.

### 9.2. Возврат на приоритетный туннель

В Wirefork возврата нет: пользователь видит иконку и переключит сам. Headless-демон мог бы неделями работать на резерве после короткого сбоя. Поэтому в wgplex правило, ушедшее на резерв, возвращается на более приоритетный туннель из `via`:

- **только туннель с `check`.** Без активной проверки после failover трафика на туннеле нет, и «жив» дал бы один свежий handshake: сервер, который отвечает на handshake, но не пропускает данные, гонял бы правило туда-обратно каждые несколько минут. Туннель без `check` возврата не даёт — правило остаётся на резерве;
- **5 минут подряд живым** (константа) — отсчёт от перехода в «жив» по успешной проверке; состояние «неизвестно» после подъёма или сброса не считается; смена сети и пробуждение обнуляют отсчёт;
- **сразу** — при явном `tunnel.enable` приоритетного туннеля и при `config.reload`: выбор делается заново (7.3);
- возврат рвёт открытые соединения правила один раз.

## 10. Конфигурация

### 10.1. Формат

Главный файл — `wgplex.yaml`, `.conf` туннелей — рядом в каталоге конфига (3); `conf` в YAML ссылается на имя файла без пути. Остальные `*.yaml` в каталоге игнорируются с предупреждением. Конфиг Wirefork переносится копированием (с переименованием файла); новое поле верхнего уровня — `control_group` (5).

```yaml
# <prefix>/etc/wgplex/wgplex.yaml

control_group: admin   # кто, кроме root и владельца, управляет (5)
ipv6_filter: true

# Порядок туннелей = приоритет при одинаковых префиксах из AllowedIPs (7.2)
tunnels:
  - name: work
    conf: work.conf            # файл в этом же каталоге (можно симлинк)
    routes: config             # AllowedIPs → таблица маршрутов
    autostart: true
    dns_domains:               # резолвить через DNS из work.conf
      - corp.example
    check: 10.0.0.1            # необязательно: ping через туннель
                               # или http(s)://… — HTTP-проверка (9)

  - name: home
    conf: home.conf
    routes: config
    autostart: false

  - name: nl
    conf: nl.conf
    routes: rules              # только маршруты из правил
    autostart: true
    check: 1.1.1.1

  - name: de
    conf: de.conf
    routes: rules
    autostart: true
    check: 1.1.1.1

services:
  youtube:
    domains: [youtube.com, googlevideo.com, ytimg.com, youtu.be, ggpht.com]
  ai:
    domains: [openai.com, chatgpt.com, anthropic.com, claude.ai, gemini.google.com]
  telegram:
    cidrs: [91.108.4.0/22, 149.154.160.0/20]

rules:
  - services: [youtube, telegram]
    via: [nl, de]
    fallback: default
  - services: [ai]
    via: [nl, de]
    fallback: block
```

**Валидация.** Уникальные имена туннелей и сервисов; существующие `conf`; ссылки правил на существующие сервисы и туннели; корректные домены и CIDR; `.conf` разбирается полностью; неизвестные ключи YAML — ошибка; у туннеля с `dns_domains` в `.conf` есть `DNS`; в `dns_domains` нет `=` (это зоны, а не точные имена); `check` — IP-адрес или URL со схемой `http`/`https` и хостом, без userinfo и fragment; один `.conf` не используется несколькими туннелями (два utun с одним ключом перебивают друг другу endpoint на сервере); `wgplex.yaml` содержит один YAML-документ; у туннеля с `routes: config` в `AllowedIPs` нет `0.0.0.0/0` и `::/0` (конфликт с основным маршрутом системы; для такого туннеля — `routes: rules`, режим «весь трафик через X» — вне v1, 19). Кроме того — права и владельцы файлов, `control_group` (5) и лимит зон (8). Собираются все ошибки, а не только первая. При любой ошибке конфиг не применяется (10.2).

Значения по умолчанию: `control_group: admin`, `ipv6_filter: true`, `autostart: false`, `fallback: default`. Поле `routes` обязательно.

Нормализация (предупреждение, конфиг применяется):

- CIDR с ненулевыми хост-битами (`10.1.2.3/16`) приводится к каноническому виду — как это делает `wg`. Одинаково для `.conf` и `wgplex.yaml`, кроме `Address`: это адрес интерфейса с длиной префикса (`10.0.0.2/24`), он хранится как задан.
- Сервис, не используемый ни одним правилом, — предупреждение.

Без предупреждения:

- адрес без префикса в `.conf` — `/32` или `/128`;
- дубликаты в `Address`, `AllowedIPs`, `DNS` (включая `x` и `x/32`) убираются.

**Ключи.** Приватные ключи остаются в `.conf` (рекомендуемые права `0600`, 5). Keychain не используется: без стабильной подписи доступ к нему сбрасывается при каждой сборке. Ключи никогда не пишутся в логи и не возвращаются по API, в том числе в текстах ошибок разбора. Тип ключа при любом форматировании (`%v`, `%#v`, JSON) выводит `(redacted)`.

### 10.2. Применение

- Демон читает каталог сам: при старте и по `config.reload` (`wgplex reload`, «Перечитать» в окне). Разбор и валидация — в демоне. За изменением файлов не следит; SIGHUP не перечитывает.
- Повторное применение: туннели остаются включёнными или выключенными по переключателям (11), новый туннель включается по `autostart`, удалённый останавливается. Работающий туннель перезапускается, только если изменился его `.conf`. Изменения YAML (`routes`, `dns_domains`, `check`, сервисы, правила) применяются без перезапуска туннелей. Выбор туннелей для правил делается заново (7.3).
- Заново берутся шлюзы и исходные DNS системы, переносятся host-route'ы до endpoint'ов. Смену сети демон отслеживает сам (6).
- Ошибка подъёма туннеля не отменяет применение: туннель остаётся включённым с ошибкой (7.2), повтор — повторное включение (`tunnel.enable`), `config.reload` или повтор подъёма (6). Ошибки подъёма — в результате `config.reload` (14).
- Предупреждение, если DNS-сервер туннеля попадает в CIDR правила с `fallback: block`: в fallback reject-маршрут отрежет и DNS через этот туннель.
- Предупреждение, если `check` (IP или IP-литерал в URL) другого семейства, чем `Address` туннеля (9).
- Ошибка при `reload` — конфиг не применяется, работает прежний; ошибки — в результате и в `status.get`.
- Ошибка при старте — туннелей нет (`configured: false`, `config_errors`), действует снимок блокировки (9.1). Копия последнего удачного конфига не хранится: это ещё одно место с ключами и поведение «работает не то, что в файле»; снимок блокировки ключей не содержит.
- Каталога нет — ошибка конфига «нет каталога», `configured: false`. Пустой конфиг (шаблон) — `configured: true`, туннелей нет.
- При каждом удачном применении (старт и `reload`) туннель без записи в переключателях (11) следует `autostart`: правка `autostart` в YAML действует с ближайшего `reload` (в Wirefork — со следующего первого применения).

### 10.3. Шаблон

Формула в `post_install_steps` (`post_install` в Homebrew 7 устарел, M0, H2, H18) создаёт каталог (`0700`) и `wgplex.yaml` (`0600`) из шаблона, если каталога нет (`unless_path_exists`), а также `var/wgplex`, `var/log/wgplex` и `var/run` (4.1). Шаблон целиком закомментирован (пустой конфиг валиден: туннелей нет, DNS не захватывается): что положить в каталог и пример 10.1. Шаблон лежит в архиве релиза как `share/wgplex/wgplex.yaml`, формула ставит его в `pkgshare`. Обновление формулы существующий каталог не трогает.

## 11. Состояние

`<prefix>/var/wgplex/state.json`, одна запись на машину:

- **переключатели** — туннели, которые включали или выключали явно (`tunnel.enable`, `tunnel.disable`, `tunnel.disableAll`), и их состояние. Туннель без записи — по `autostart` (10.2). Каждое удачное применение конфига (старт и `reload`) убирает туннели, которых нет в конфиге;
- **пауза** — `paused`;
- **снимок блокировки** — `block`: CIDR и домены правил `fallback: block` последнего удачно применённого конфига (9.1).

Запись атомарная (временный файл в том же каталоге и `rename`). Файл не читается или битый — предупреждение в лог, туннели по `autostart`, без паузы, снимка блокировки нет.

Не сохраняется: на каком туннеле сейчас правило, вердикты здоровья, динамические адреса. После перезапуска правила начинают с первого туннеля `via`, адреса появляются по DNS-запросам.

## 12. Пауза и «Выключить все»

| | Пауза | Выключить все |
|---|---|---|
| Смысл | временно: как Mute, поверх переключателей | постоянно: снимает переключатели |
| Переключатели туннелей | не меняются | все — выключены |
| Возврат | «Возобновить» — поднимается прежний набор | включать туннели по одному |
| Переживает перезапуск | да | да |
| CLI | `wgplex pause` / `wgplex resume` | `wgplex down -all` |
| Меню | «Приостановить» / «Возобновить» | нет (окно) |

- На паузе туннели опущены, `tunnel.enable`/`disable` меняют переключатели, но ничего не поднимают; `wgplex up` на паузе — успех с пометкой «starts on resume».
- Правила в паузе и после «Выключить все» уходят в fallback; `fallback: block` продолжает блокировать (9.1): обычный пользователь не может обойти запрет админа паузой. Захват DNS не меняется (зоны — функция конфига, 8).
- «Выключить все» — разовое действие над туннелями конфига на этот момент, не режим (режим — пауза). Туннель, добавленный позже `reload`'ом, следует `autostart`.
- Пауза общая для всех пользователей, право — как у остальных изменяющих методов.

## 13. CLI

```
wgplex status [-json]            туннели, handshake, трафик, проверки, правила
wgplex explain <домен|IP> [-json] какое правило, какой туннель и почему
wgplex routes [-json]            текущие маршруты: из конфига и динамические
wgplex up <туннель>              включить (запоминается)
wgplex down <туннель> | -all     выключить один или все (запоминается)
wgplex pause | resume            пауза (12)
wgplex reload                    демон перечитывает конфиг
wgplex check [-config dir] [-json] проверить конфиг без демона и root
wgplex daemon [-v]               демон (из brew services)
wgplex version
```

- Вывод — текст; `-json` у команд только для чтения и `check` — те же структуры, что в API.
- `wgplex status` показывает все правила, отмечая ушедшие на резерв или в fallback, и паузу. Туннели — с колонкой `CHECK`: RTT, `fail N` или `-` без `check`; у мёртвого туннеля — причина.
- Предупреждения конфига — в `wgplex reload` и `wgplex status`.
- Коды выхода: `0` — успех, `1` — ошибка (в том числе нет прав), `2` — неверные аргументы, `3` — демон недоступен (нет сокета, отказ, таймаут).
- Нет прав — `permission denied: up/down/reload require root, the config owner or membership in group "<группа>"`.
- Отладочные флаги: `-socket` у клиентских команд; `-config`, `-socket`, `-state`, `-log` у `daemon`.
- Версия CLI отличается от `version` демона в `status.get` (после `brew upgrade` без перезапуска службы, 16.4) — предупреждение в stderr с командой перезапуска; код выхода не меняется. `wgplex version` печатает обе.
- Тексты CLI и демона — на английском.

## 14. API

JSON-RPC 2.0 на `github.com/mrFokin/jrpc/v2` (Echo v5), HTTP поверх unix-сокета, `POST /rpc`. Сокет передаётся Echo через `StartConfig.Listener`; uid из `LOCAL_PEERCRED` кладётся в контекст соединения (`http.Server.ConnContext` через `StartConfig.BeforeServeFunc`) и проверяется в обработчике метода — отказа на уровне HTTP нет. Push-уведомлений нет, только опрос. Публичный контракт — `docs/api.md` (английский).

- Сокет — `0666` (5). Файл сокета, на котором никто не отвечает (после падения), удаляется при старте; если отвечает — это второй экземпляр, он завершается с ошибкой. При остановке файл удаляется.
- Ключи не попадают в ответы, в том числе публичные (10.1).

| Метод | Параметры | Права | CLI |
|---|---|---|---|
| `status.get` | — | все | `status` |
| `diag.explain` | `{query}` | все | `explain` |
| `diag.routes` | — | все | `routes` |
| `config.reload` | — | управление | `reload` |
| `tunnel.enable` | `{name}` | управление | `up` |
| `tunnel.disable` | `{name}` | управление | `down` |
| `tunnel.disableAll` | — | управление | `down -all` |
| `daemon.pause` | — | управление | `pause` |
| `daemon.resume` | — | управление | `resume` |

- Правило имён — `объект.глагол`, без булевых параметров. Изменяющие методы идемпотентны, с одним исключением: `tunnel.enable` туннеля в состоянии `error` поднимает его заново (повтор подъёма, 6).
- `status.get` — туннели в порядке конфига (переключатель, состояние, причина `dead` или текст `error`, интерфейс и адреса, число маршрутов, пиры: endpoint, handshake, трафик; результат `check` — RTT последнего успеха или число неудач подряд), правила в порядке конфига (текущий туннель, на резерве, в fallback), `configured`, ошибки последнего неудачного применения (`config_errors`) и предупреждения применённого конфига, `icon`. Плюс: `api_version` (целое, сейчас `1`), `version` (движка), `can_control` (для вызывающего), `control_group`, `paused`, `config_dir`, `log_path`. Для тех, кто не управляет, ответ урезан (5, «Видимость»).
  - У туннеля `enabled` — **переключатель** (11), а не «запущен»: на паузе он сохраняется; фактическое состояние — `state` (`off | starting | up | dead | error`). `dead` — utun есть, проверка здоровья (9) считает туннель мёртвым; `error` — не поднялся.
  - У правила на резерве или в fallback — причина `reason`: `dead` (туннели `via` мертвы или не поднялись), `disabled` (выключены переключателем), `paused`. По ней приложение отличает сбой от намеренного действия (17.6).
  - `icon` — `off | on | warn | paused`, по приоритету: `configured: false` или ошибка захвата DNS — `warn`; иначе пауза — `paused`; иначе ошибка конфига или включённый туннель в `dead` или `error` — `warn` (туннель в `starting` и правило в fallback из-за выключенного туннеля иконку не меняют); иначе хотя бы один туннель `up` — `on`; иначе `off`.
  - `configured: false` с `config_errors` — «запущен без туннелей».
- `config.reload` — прочитать каталог, проверить, применить (10.2). Результат — предупреждения конфига и ошибки подъёма туннелей: конфиг применён. Конфиг не прошёл проверку — ошибка `1`, работает прежний.
- Ошибки: `1` — конфиг не прошёл проверку (`config.reload`; `data`: ошибки и предупреждения), `2` — конфиг не применён (`tunnel.*` при `configured: false`; `daemon.pause`/`resume` работают и без конфига), `3` — неизвестный туннель, `4` — туннель не поднялся, **`5` — нет прав** (`data`: `control_group`). Отказ в правах — ошибка JSON-RPC, не HTTP 403: чтение доступно всем.
- **Совместимость:** в пределах `api_version` поля и методы только добавляются, клиент игнорирует незнакомые поля. Несовместимое изменение — следующая `api_version`.

## 15. Логи

- `log/slog`; демон сам пишет `<prefix>/var/log/wgplex/wgplex.log` и подменяет им stdout и stderr (`dup2` на fd 1 и 2 — туда попадают и паники Go; иначе после ротации fd 1 писал бы в архив).
- До `dup2` stderr и stdout — тот же файл через `log_path`/`error_log_path` формулы (16.4): без них launchd отдаёт `/dev/null`, и ранние ошибки теряются (M0, H5).
- Ротация в демоне: writer считает записанные байты (под мьютексом); при 5 МБ файл переименовывается в `wgplex.log.1` (старый `.1` — в `.2`, `.2` удаляется), открывается новый и снова `dup2` на fd 1 и 2. newsyslog, pid-файл и SIGUSR1 не нужны (SIGUSR1 игнорируется, 4.1).
- Файл и архивы — `0640`, владелец root, группа — `control_group` (без применённого конфига — `admin`): лог читают окно приложения и `tail` у тех, кто управляет. Остальным раздел логов в приложении показывает «нужно членство в группе …». Имена из DNS-запросов — только на уровне debug (`-v`).

### 16.4. Формула

- `wgplex` в `mrFokin/homebrew-tap` (`brew install mrfokin/tap/wgplex`): **готовый universal-бинарник** из релиза, Go у пользователя не нужен, установка — секунды. Так принято в собственных tap (например, `hashicorp/tap`); собрать самому — `make build` из репозитория. Формулы карантин не получают, Gatekeeper бинарник не проверяет. `depends_on :macos`.
- Установка — только по полному имени `brew install mrfokin/tap/wgplex`: Homebrew 7 загружает формулы стороннего tap только при доверии, полное имя доверяет сам (иначе — `brew trust mrfokin/tap`, M0, H1).
- `service do`: `run [opt_bin/"wgplex", "daemon"]`, `require_root true`, `keep_alive successful_exit: false` (4.1), `log_path` и `error_log_path` — `var/"log/wgplex/wgplex.log"` (15).
- **Запуск — `sudo brew services start --sudo-service-user=root wgplex`.** Без `--sudo-service-user=root` brew делает root владельцем бинарника и симлинков формулы, после чего `brew upgrade`, `cleanup` и `uninstall` от пользователя оставляют мусор или падают (M0, H3, H8–H13); с опцией владельцы не меняются, демон всё равно root (H16). Защиты бинарника от владельца prefix это не убирает — её нет и так (5). Опция нужна при каждом `start` и `restart`.
- **`brew upgrade` службу не перезапускает** (M0, H8): новая версия — после `sudo brew services restart --sudo-service-user=root wgplex`.
- `brew services` без `sudo` управляет не службой root, а копией от пользователя (M0, H7).
- `caveats`: команда запуска с `--sudo-service-user=root` (строка, которую brew добавляет сам, — без опции), перезапуск после `upgrade`, `brew services` только через `sudo`; где конфиг; что root запускает бинарник из prefix владельца (5).
- `test do`: `wgplex version`; шаблон из `pkgshare` копируется в `testpath`, затем `wgplex check -config testpath` (без `-config` `check` прочитал бы настоящий `etc/wgplex`).
- Удаление — строго в этом порядке: `sudo brew services stop wgplex` (выгружает службу и удаляет plist), затем `brew uninstall wgplex`. Наоборот — plist остаётся, а `brew services` его уже не видит: `uninstall` снимает доверие к формуле (M0, H17). Каталог конфига остаётся (`etc` brew не удаляет), `var/wgplex` и `var/log/wgplex` — тоже (файлы root, `sudo rm`). При остановке демон снимает маршруты и захват DNS (9.1).
- CI — вне v1.

## 17. Приложение Wgplex.app

Отдельный репозиторий `mrFokin/wgplex-app`; раздел переносится туда при его создании.

### 17.1. Поставка

- **Основной канал — cask `wgplex-app`** в `mrFokin/homebrew-tap`: `depends_on formula: "mrfokin/tap/wgplex"`, `depends_on macos: ">= :ventura"`, `.dmg` из релиза GitHub. Запасной — тот же `.dmg` вручную (universal, ad-hoc подпись).
- Установка: `brew trust mrfokin/tap`, затем `brew install --cask mrfokin/tap/wgplex-app`. Homebrew 7 доверяет по полному имени только самому cask, а формулу-зависимость из того же tap без `brew trust` не загружает (M0, K4, K11).
- Developer ID пока нет. Первый запуск (M0, K6, K7): диалог «"Wgplex" Not Opened — Apple could not verify…», кнопка «Done» (не «Move to Trash»); затем «Системные настройки → Конфиденциальность и безопасность» → «"Wgplex" was blocked to protect your Mac» → «Open Anyway» → пароль администратора. Тексты — в README. С подписью меняется только этап сборки.
- **Обновление через `brew upgrade --cask` повторного разрешения не требует:** Homebrew сохраняет каталог `.app` и переносит одобрение (M0, K8, K9). Ручная замена из `.dmg` — требует «Open Anyway» снова (K10).
- Обновления: раз в сутки запрос последнего релиза через GitHub API (если включено «Проверять обновления»). Новая версия — одно уведомление на версию (17.6) и баннер в окне до обновления: команда `brew upgrade --cask wgplex-app` с копированием и ссылка на страницу релиза. Sparkle не используется.

### 17.2. Движок

- Сокет ищется по `/opt/homebrew/var/run/wgplex.sock`, затем `/usr/local/var/run/wgplex.sock`; переопределение — в настройках.
- Установлен ли движок — по `<prefix>/opt/wgplex/bin/wgplex`, работает ли — по сокету: при остановке службы демон удаляет файл сокета, и «сокета нет» не значит «не установлен».
- Три состояния без движка: бинарника нет — «wgplex не установлен», «Как установить…»; бинарник есть, сокета нет или он не отвечает — «Демон не запущен», команда `sudo brew services start --sudo-service-user=root wgplex` с копированием; `api_version` меньше нужной — «Обновите wgplex»: `brew upgrade wgplex` и `sudo brew services restart --sudo-service-user=root wgplex`.
- «Выход» закрывает только приложение: туннели принадлежат машине. Остановка демона — `brew services`, не GUI.

### 17.3. Меню

`NSStatusItem` + `NSMenu` (AppKit): свежий `status.get` при открытии (`menuNeedsUpdate`), обновление раз в 1–2 с, пока меню открыто (таймер в `.common` mode); в фоне — раз в 10 с для иконки.

```
✓ nl
✓ de  ⚠
  work
──────────
⚠ youtube на резерве        (только когда есть проблема)
──────────
Приостановить               (на паузе — «Возобновить», галочки серые)
Открыть Wgplex…
Выход
```

- Галочка — туннель включён, щелчок переключает. ⚠ — включён, но мёртв или не поднялся.
- Строка проблемы (правило на резерве или в fallback, ошибка конфига, демон недоступен) открывает окно на нужном месте.
- Без права управления (`can_control: false`) туннели и «Приостановить» неактивны.
- Иконка — template: контурный щит (всё выключено), залитый (работает), с «!» (проблема), с паузой.

### 17.4. Окно

Боковая панель и содержимое раздела (SwiftUI). Приложение без значка в Dock (`LSUIElement`); значок появляется, пока окно открыто.

- **Панель действий** во всех разделах: Приостановить/Возобновить, Выключить все, Перечитать конфиг. Без права управления — неактивны.
- **Баннер** сверху: ошибка конфига, демон недоступен, пауза, правило на резерве, доступна новая версия.
- **Туннели:** список с переключателями; детали выбранного — endpoint, интерфейс и адрес, handshake, трафик, маршрутов, проверка.
- **Правила:** сервисы, `via`, текущий туннель, состояние.
- **Диагностика:** поле `explain`, таблица маршрутов.
- **Логи:** хвост файла из `log_path`, поиск, фильтр по уровню, дочитывание, пока раздел открыт. Без членства в `control_group` файл недоступен (15) — «нужно членство в группе …».
- **Открыть папку конфига** — если `config_dir` доступен текущему пользователю на чтение (на практике владелец); иначе — путь и «Конфиг правит администратор».
- **Настройки** (⌘,): запуск при входе, уведомления, путь к сокету, проверка обновлений.

### 17.5. Автозапуск

- `SMAppService.mainApp` (видно в «Объектах входа» → «Open at Login» одной записью под своим именем). С ad-hoc подписью регистрация — сразу `enabled`, без одобрения; система один раз показывает уведомление. Регистрация переживает обновление бандла с другим cdhash и перезагрузку — запись та же (M0, S1–S5). После `unregister` запись остаётся выключенной, повторная регистрация уведомления не даёт (S6).
- По умолчанию выключен. При первом запуске — один вопрос «Запускать Wgplex при входе?» и запрос разрешения на уведомления.
- Каждый пользователь включает сам. Для всех пользователей сразу — команда для админа в README (plist в `/Library/LaunchAgents`), без привилегированного кода в приложении.

### 17.6. Уведомления

Приложение сравнивает соседние ответы `status.get` (раз в 10 с); движок не меняется. Работают, пока приложение запущено.

| Событие | Пример |
|---|---|
| Туннель включён, но умер или не поднялся, и правила ушли на резерв или в fallback | «nl не отвечает: youtube, ai → de» |
| Восстановление | «nl снова работает, youtube через nl» |
| Ошибка конфига при `reload` | «Изменения конфига не применены: 2 ошибки. Работает прежний конфиг» |
| Ошибка конфига при старте | «wgplex запущен без туннелей: конфиг с ошибками» |
| Демон пропал / вернулся | «wgplex не работает» |
| Новая версия приложения (17.1) | «Доступна Wgplex 1.3» — один раз на версию |

- Не уведомляет о намеренных действиях — в том числе сделанных другим пользователем или из CLI: о резерве и fallback уведомляет только при `reason: dead` (14), паузу и переключения не замечает. Не уведомляет о результате собственного «Перечитать» — он виден в окне.
- События одного опроса — одно уведомление; о «мигающем» туннеле — не чаще раза в 5 минут.
- Одна галочка в настройках, по умолчанию включена. Щелчок открывает окно на нужном разделе.

### 17.7. Сборка

Swift Package, macOS 13+, без сторонних зависимостей. `make dmg` — `swift build -c release --arch arm64 --arch x86_64`, бандл, ad-hoc подпись с постоянным требованием `codesign --sign - -r='designated => identifier "io.github.mrfokin.wgplex"'` (иначе требование — cdhash, и при `brew upgrade --cask` Homebrew пишет «signer changed» и не переносит одобрение, M0, K8, K9), `hdiutil create`; релиз — `gh release create` с `.dmg` (16.1). Код — копия `app/` Wirefork (клиент RPC, модели статуса) без чтения и отправки конфига; меню переписывается на AppKit. Логика (клиент, представление статуса, вычисление уведомлений) — в библиотечном таргете под XCTest, с фейковым сервером API.

## 18. Ограничения v1

- Не больше 1000 зон захвата DNS (8). Зона чужого VPN, более длинная, чем наша (`www.example.com` при нашей `example.com`), забирает свои имена.
- Имена внутри наших зон, которым правило не подходит (`mail.google.com` при `=google.com`), и имена правил в `fallback: default` уходят на DNS первичного сервиса. При работающем чужом VPN с `[""]` без wgplex они шли бы на DNS этого VPN — расхождение или DNS-утечка для таких имён.
- **FileVault:** после перезагрузки диск заблокирован до ввода пароля в preboot, macOS и демон не запускаются — туннели поднимаются только после разблокировки. Для машин без монитора — без FileVault или `fdesetup authrestart` для плановых перезагрузок (от отключения питания не спасает). В README.
- **TCC:** `.conf` по симлинку из `~/Documents`, `~/Desktop`, `~/Downloads`, iCloud Drive и со съёмных томов демон не читает, хотя `wgplex check` из Terminal читает (5).
- Гарантия `fallback: block` — пока служба включена; не действует при остановленной службе и в секунды загрузки до старта демона (9.1).
- Ограничения DNS касаются только конфигов с доменами: без зон системный DNS не захватывается (8).
  - Браузеры с включённым вручную DoH и iCloud Private Relay обходят системный DNS — правила по доменам на них не действуют.
  - Мимо резолвера wgplex идут также запросы приложений, привязанных к физическому интерфейсу (scoped-запросы), и имена из `/etc/resolver/*`.
  - Перезапуск configd убирает ключ захвата DNS; до его восстановления демоном (8) запросы идут мимо резолвера.
  - CNAME-цепочка не анализируется: сторонний домен, указывающий на CDN сервиса, нужно добавлять явно.
- Туннели и правила общие: трафик всех пользователей машины идёт по конфигу владельца.
- Root запускает бинарник из каталога владельца prefix (5).
- Уведомления — только пока у пользователя запущено приложение.
- Wirefork и wgplex на одной машине друг другу маршрутов не удаляют (свои метки, 4.1), но их правила на одних префиксах конфликтуют, а захват DNS у каждого свой: одновременная работа не поддерживается.
- Без Developer ID приложение разрешается вручную при установке и при каждой ручной замене из `.dmg`; `brew upgrade --cask` — без этого.
- При переключении правила на другой туннель открытые соединения рвутся (в том числе при возврате, 9.2).
- Пересечение адресов туннеля с локальной сетью (например, домашняя `192.168.1.0/24` в отеле с той же подсетью) не разрешается автоматически, в лог пишется предупреждение; маршрут ставится. Префикс, равный подсети локальной сети, не ставится — это чужой маршрут (7.2).
- Другие VPN на машине при маршрутизации не учитываются.
- Пробуждение определяется по скачку времени (6), с задержкой до 2 с. Ручная перестановка часов вызывает лишнюю пересинхронизацию.
- Основной маршрут через интерфейс без шлюза (`ppp*`, `link#N`) считается отсутствием физического шлюза: endpoint'ы получают blackhole, туннели в такой сети не работают. Поэтому туннели wgplex не работают и поверх PPPoE-подключения.

## 19. Вне v1

- Редактор конфига в окне (для владельца): структурная правка через CLI на Go (`wgplex config …` поверх `yaml.v3` `Node`, с сохранением комментариев), проверка — `wgplex check -json`.
- Пункт «Запускать для всех пользователей» в приложении.
- Хуки на события (скрипт при уходе правила на резерв).
- CI: `make check` на push, релиз и обновление формулы по тегу.
- Developer ID, подпись и нотаризация приложения.
- Режим «весь трафик через туннель X» (`0/1` + `128/1`).

## 20. Spike перед разработкой

Этап M0, в VM tart через `scripts/vm.sh` (CLAUDE.md, «Root и система»). Подготовка:

- образ `wgp-base`: Homebrew, гостевой агент tart (общий буфер обмена с хостом), вход по SSH только по ключу, `sudo` для `admin`;
- bridged-сеть поверх Wi‑Fi хоста; NAT tart — только при выключенных туннелях хоста: трафик VM идёт по маршрутам хоста, адреса за utun недоступны (M0, B3);
- WireGuard-сервер во второй VM — тестовый стенд с M2 (21.1), не для M0.

Проверки:

1. **Точечный захват DNS:** `SupplementalMatchDomains` со списком зон (сотни доменов), приоритет перед `[""]` чужого VPN, `ServerPort` с нестандартным портом.
2. **`dsmemberutil checkmembership`:** вложенные группы, время вызова, поведение для несуществующих uid и группы. Итог — `mbr_check_membership` (5).
3. **`SMAppService.mainApp` с ad-hoc подписью:** регистрация, обновление на новую сборку, перелогин.
4. **Неподписанный cask на Homebrew 7** из стороннего tap: ставится ли, что при `brew upgrade --cask`.
5. **Формула со службой от root:** `service do … require_root true`, `sudo brew services start`, затем `upgrade`, `uninstall`, `cleanup` от пользователя — владельцы путей, перезапуск службы, stderr до `dup2`.

Факты — `docs/plans/m0-spike.md`, «Факты spike».
